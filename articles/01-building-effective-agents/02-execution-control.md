# 执行控制是统一抽象的核心

## 文章中的关键观点

文章中的多种模式虽然表面差异很大，但都在回答同一个问题：任务执行到当前状态以后，下一步如何被决定。

## 我们的架构分析

如果把系统抽象为：

```text
状态 → 决策 → 动作 → 新状态
```

那么工作流和智能体只是“决策”部分的控制来源不同：

```text
工作流：代码 / 图 → 下一步
智能体：模型 + 上下文 → 下一步
```

这意味着统一执行内核不应该把“工作流节点”作为唯一核心原语，也不应该把“模型循环”直接写死为唯一核心原语。

更稳定的核心是：

- 当前执行状态；
- 一次动作；
- 动作结果；
- 状态如何被更新；
- 谁决定下一动作。

执行控制可以由代码、模型、人工或外部事件共同参与。

## 对 Agent Platform 的影响

统一运行时需要允许上层插入不同的控制策略。例如：

- 确定性流程由工作流控制器推进；
- 开放任务由智能体执行框架（Harness）推进；
- 高风险动作由人工审批后继续；
- 定时器和 Webhook 可以重新触发执行。

运行时负责可靠执行事实，而不是替上层决定所有策略。

## 核心结论

> **统一运行时应稳定承载执行事实和状态变化，把“下一步怎么决定”留给可替换的执行控制策略。**
