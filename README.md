# Agent Platform

> **Agent Platform 的核心，不是“跑一个智能体循环”，而是把动态组装、非确定、长期、并行、可编程的智能执行过程，约束在持久、可恢复、可验证、可观测、可治理、能够持续演进的生产系统中。**

**在线阅读：<https://felixjichao.github.io/agent-platform/>**

## 为什么需要 Agent Platform

过去我们很容易这样理解智能体：

```text
提示词
  ↓
LLM
  ↓
工具调用
  ↓
结果
  ↓
LLM
  ↓
...
```

这个最小循环足够解释一个智能体 Demo，却远远不足以解释一个生产级智能体系统。

当智能体开始长时间运行、调用越来越多的工具、操作真实业务系统、处理中间文件和大量数据、跨多个会话延续工作、动态创建子智能体、执行生成代码并自主规划和恢复时，真正困难的问题就不再是：

> **怎么让模型调用工具？**

而是：

> **怎么治理一个非确定的智能执行过程？**

本项目希望建立一套足够稳定的智能体软件架构，使对话助手、科研助手、知识库、工作流、编程助手、自主智能体等不同产品形态，可以共享同一套底层执行基础设施。

# 核心判断

下面是当前研究形成的 13 个核心架构判断。

## 01. 应用形态不等于执行范式

对话、科研助手、知识库、编程助手、行业应用，是产品形态。

直接执行、工作流、智能体循环、程序化工具调用（PTC）、多智能体，是执行范式。

```text
产品形态
对话 · 科研 · 知识库 · 编程助手
              │
              │ 不等于
              ▼
执行范式
直接执行 · 工作流 · 智能体循环 · PTC · 多智能体
```

同一个产品可以混合多种执行策略，因此不应该为每一种智能体产品重新实现一套运行时。

## 02. 工作流与智能体的真正区别，是谁拥有执行控制权

工作流中，下一步主要由预定义代码或图决定；智能体中，下一步主要由模型根据当前上下文动态决定。

```text
静态工作流
    ↓
动态工作流 / 计划
    ↓
智能体循环
```

二者更像一条连续谱，而不是截然分开的两套技术。

> **工作流图是输入表达；智能体图更接近运行时结果。**

## 03. 运行时管事实，执行框架管策略

这是整套架构最重要的边界之一。

```text
业务层
→ 要完成什么

执行框架
→ 当前准备怎么完成

运行时
→ 实际发生了什么
```

规划器、待办、评估器、上下文策略、委派策略、完成策略，都可能随着模型能力提升而变化。

而工作单元（Work）、会话（Session）、运行（Run）、事件（Event）、状态、动作（Action）、结果（Result）、制品（Artifact）、恢复这些执行事实应该保持稳定。

> **运行时应稳定；执行框架应可替换、可简化，甚至最终消失。**

## 04. 工作单元承载长期连续性，而不是智能体

一个长期任务不应该依赖“这个智能体永远不能忘记”。真正持久的应该是：

```text
工作单元
├── 目标
├── 任务
├── 共享资源
├── 工作前沿
├── 制品
├── 工作空间
├── 进度
└── 会话
```

智能体可以丢失上下文、结束会话、更换模型或执行框架，甚至被新的智能体接管，但工作单元必须继续存在。

> **智能体可以忘记、退出或者被替换；工作单元必须记住。**

## 05. 事件是事实，状态和上下文都是投影

统一运行时的基本关系：

```text
动作 / 结果
    ↓
   事件
    ↓
 事件日志
    ↓
   状态
```

其中：

```text
事件   → 已经发生的事实
状态   → 根据事实计算出的当前视图
上下文 → 当前模型实际需要看到的工作集
```

因此：

> **事件是事实，状态是投影，上下文是查询结果。**

快照、摘要、上下文压缩都不能反过来成为真实历史。

## 06. 上下文是工作集，不是整个世界

生产级智能体不应该尝试把所有信息永久塞进上下文窗口。

更合理的模型是：

```text
会话
状态
记忆
笔记
制品
工作空间
技能
能力
外部资源
     ↓
上下文构建器
     ↓
   上下文
```

上下文应该可以丢弃、可以重建，并按照当前目标动态投影、按需加载知识和能力。

> **上下文包含的是地图，而不是整个世界。**

模型需要的是当前工作的地图，而不是整个世界。

## 07. LLM 应该是控制面，而不是数据面

很多智能体系统让模型同时承担推理、编排和数据搬运，结果大量 Token 被消耗在循环、过滤、关联、聚合和格式转换上。

更合理的是：

```text
智能体 / 执行框架
= 执行控制面

智能体工作环境
= 数据面 + 动作面
```

程序化工具调用（PTC）体现了这种方向：

```text
模型
 ↓ 生成程序
程序
 ├── 工具 A
 ├── 工具 B
 ├── 循环
 ├── 过滤
 └── 聚合
 ↓
观察
 ↓
模型
```

> **一个模型推理步骤，可以展开成多个受治理的环境动作。**

## 08. 工具、技能、MCP、执行框架是四种不同东西

```text
工具
→ 能做什么动作

技能
→ 这类任务应该怎么做

MCP
→ 如何连接外部系统

执行框架
→ 当前任务现在怎么推进
```

因此：

> **MCP 是连接标准，不是能力设计标准。**

一个后端 API 或 MCP 工具，也不应该直接等于面向智能体的工具。

```text
后端 API / MCP
      ↓
能力适配器
      ↓
语义能力
      ↓
面向智能体的工具
```

真正的设计单位应该是对智能体有意义的工作能力，而不是后端 API 端点。

## 09. 智能体本身可以是动态组装出来的

随着技能、工具、知识、上下文都可以按需加载：

```text
基础智能体
+ 选中的技能
+ 选中的工具
+ 召回的知识
+ 任务上下文
       ↓
实际工作的智能体
```

因此不必为每一种业务场景预先创建一个固定智能体。平台更应该建设能力目录、能力发现和运行时组合，而不是不断增加静态智能体类型。

> **智能体使用能力，但不应该拥有能力。**

## 10. 多智能体的关键不是智能体数量，而是工作前沿

复杂任务并不自动意味着需要多智能体。只有当任务具备可并行、上下文相对独立、结果可合并、依赖密度较低等特征时，多智能体才真正产生价值。

真正决定并行度的是：

> **当前有多少个可以独立领取、独立推进、独立验证的工作项（Work Item）。**

这些工作项共同构成工作前沿（Work Frontier）。

> **多智能体的核心是工作调度器，而不是智能体调度器。**

同时：

```text
委派
→ 传递目标

授权
→ 单独推导最小权限
```

> **委派不应该默认复制权限。**

## 11. 评估不是测试附件，而是能力规格

对非确定智能体，仅仅写一个预期输出通常不够。更合理的基本单位是试验（Trial）：

```text
任务
 ↓
试验
├── 执行框架修订版本
├── 环境
├── 追踪
├── 结果
└── 评分结果
```

必须区分：

```text
追踪 → 智能体是怎么做的
结果 → 最终真实结果是什么
```

能力契约同时包含目标、验收标准、质量标准、评估契约和证据要求。

> **执行框架说明怎么实现；评估说明怎么证明。**

能力评估用于探索能力边界，回归评估用于守住已经获得的能力。

## 12. 智能体安全的本质，是控制智能体能触达到多大的世界

模型变得更可靠，并不意味着系统自动更安全。

```text
部署风险
≈ 失败概率 × 影响半径
```

提示词、模型训练、分类器、HITL 可以降低失败概率；真正限制最大后果的，是确定性边界：

```text
文件系统
网络
凭据
能力
数据
记忆
其他智能体
外部系统
```

因此：

> **隔离控制的本质是可达范围控制。**

每个工作单元、运行、子智能体都应该拥有尽可能小的可达世界。

最终授权也不应该只是 `github_access = true`，而应该围绕：

```text
主体
× 委派
× 能力
× 资源
× 范围
× 时长
× 工作单元上下文
```

构建。

> **治理决定边界画在哪里；基础设施保证智能体越不过这条边界。**

## 13. 自主性不是模型属性，而是部署治理结果

同一个模型在不同执行框架、权限范围、风险边界、产品默认设置和人工监督方式下，会表现出完全不同的实际自主性。

```text
执行策略
→ 当前任务怎么推进

自主性
→ 在既定边界内，智能体可以自己决定多少
```

因此，自主性不应该被建模成固定等级。系统应根据风险、可逆性、可达范围、验证能力和人工监督能力动态分配自主空间，并把中断、纠偏、主动升级等控制权转移记录为执行事实。

> **生产级智能体的目标不是最大化自主性，而是在可验证、可观察、可干预的边界内，最大化有用的自主性。**

# 智能体软件栈

上述原则最终形成了当前的七层软件栈：

```text
┌───────────────────────────────────────────────┐
│ L7 业务 / 产品                                │
│ 目标 · 项目 · 业务任务                        │
├───────────────────────────────────────────────┤
│ L6 能力契约                                   │
│ 验收标准 · 质量标准 · 评估契约                │
├───────────────────────────────────────────────┤
│ L5 能力工程                                   │
│ 技能 · 工具 · 能力发现 · MCP                  │
├───────────────────────────────────────────────┤
│ L4 执行策略                                   │
│ 工作流 · 智能体循环 · PTC · 多智能体          │
├───────────────────────────────────────────────┤
│ L3 统一运行时                                 │
│ 工作单元 · 会话 · 运行 · 事件 · 状态          │
│ 动作 · 观察 · 制品 · 恢复                      │
├───────────────────────────────────────────────┤
│ L2 智能体工作环境                             │
│ 工作空间 · 执行 · 验证                        │
│ 能力代理 · 沙箱                               │
├───────────────────────────────────────────────┤
│ L1 基础设施 / 真实世界                        │
│ API · SaaS · 数据库 · 浏览器 · 文件 · 计算    │
└───────────────────────────────────────────────┘
```

横向贯穿整个软件栈：

```text
上下文 / 记忆
评估
可观测性 / 追踪
安全 / 治理
人工监督
注册表 / 版本管理
预算 / 成本
```

每层只回答一个核心问题：

| 层 | 核心问题 |
|---|---|
| 业务 / 产品 | 要完成什么？ |
| 能力契约 | 什么叫真正具备这项能力？ |
| 能力工程 | 智能体可以学什么、做什么？ |
| 执行策略 | 当前任务怎么推进？ |
| 统一运行时 | 实际发生了什么？ |
| 工作环境 | 智能体能观察和作用于什么世界？ |
| 基础设施 | 真正的资源在哪里？ |

# 一个更完整的智能体心智模型

生产级智能体不再只是：

```text
LLM + 工具 + 循环
```

而更接近：

```text
业务目标
   ↓
能力契约
   ↓
动态能力组装
   ↓
执行框架 / 执行策略
   ↓
统一运行时
   ↓
智能体工作环境
   ↓
真实世界
```

同时，上下文 / 记忆、评估 / 验证、追踪 / 可观测性、安全 / 治理、人工监督贯穿整个执行过程。

> **Agent Platform 本质上是一套智能执行基础设施。**

# 为什么做这个项目

智能体领域正在快速出现新的概念：智能体循环、工作流、执行框架、上下文工程、记忆、技能、工具、MCP、PTC、多智能体、评估、沙箱、智能体身份、自主性、人工监督。

单独理解每个概念并不困难。困难的是：

> **它们究竟属于哪一层？彼此是什么关系？什么应该成为稳定平台抽象，什么只是当前模型时代的临时脚手架？**

本项目通过持续阅读和分析智能体工程实践，逐步建立统一的平台架构。

不是简单整理文章来源，而是保留：

```text
文章来源
   ↓
逐节分析
   ↓
架构推导
   ↓
Agent Platform 演进
```

整个过程。

# 一句话总结

> **不要把 Agent Platform 理解成一个更复杂的智能体循环。**
>
> **它真正要解决的是：如何把非确定的智能执行，变成可以进入生产环境的软件系统。**
