# L2 智能体工作环境

> **智能体工作环境负责向智能体提供一个可持续修改、可执行、可观察、可验证，并且能够真正落实安全与治理边界的工作世界。**

## 1. L2 回答什么问题

L2 不决定任务应该怎样推进，也不管理运行生命周期。它回答的是：

```text
工作空间
→ 在什么持续状态上工作？

执行器
→ 怎样对真实世界执行动作？

观察
→ 智能体应该看到什么？

验证
→ 系统怎样确认当前世界状态满足明确条件？
```

上下层边界是：

```text
L5 能力工程
→ 定义能做什么，以及能力需要什么条件

L4 执行策略
→ 决定现在做什么、何时验证

L3 统一运行时
→ 管理动作、执行尝试、可靠性与生命周期

L2 智能体工作环境
→ 真正执行、观察、验证并落实约束

L1 基础设施 / 真实世界
→ 提供文件、计算、网络、API、SaaS、数据库等真实资源
```

一句话：

> **L4 决策，L3 协调，L2 行动、观察、验证并执行边界，L1 提供真实世界。**

## 2. L2 只固定四个核心语义

第一版不需要把工作发现、所有权、租约、远程工作空间、Worker 调度等机制都做成核心领域对象。L2 的稳定核心只保留：

```text
智能体工作环境
│
├── 工作空间
│   └── 工作状态连续性
│
├── 执行器
│   └── 真实动作执行
│
├── 观察
│   └── 面向智能体的世界投影
│
└── 验证
    └── 面向系统的世界状态判定
```

沙箱、能力代理、凭据解析、网络限制、数据流策略、资源限制等是横切执行机制，用来约束这四个核心语义，但不取代它们。

## 3. 工作空间不是目录，但本地目录是完全合法的第一版实现

工作空间是一次持续工作过程中可被读取和修改的工作状态边界。对本地 Coding Agent，最简单的实现可以只是：

```text
workspace = /work/project
```

里面保存代码、文件、中间结果和生成内容。第一版不需要额外建设工作空间服务、资源注册表、统一版本系统或快照服务。

工作空间需要固定的核心语义只有：

1. **可寻址**：执行器能够定位当前工作状态；
2. **可持续**：执行器或沙箱退出后，工作状态不应因此自动消失；
3. **与运行生命周期解耦**：同一个工作空间可以被多个运行顺序继续使用；
4. **不属于运行时状态**：运行时保存工作空间引用，而不是把文件树、浏览器状态等塞进执行检查点。

因此：

```text
Workspace lifetime ≠ Run lifetime
Workspace lifetime ≠ Sandbox lifetime
Workspace contents ≠ Runtime state
```

工作空间快照、分支、变化集、合并、资源版本等都可以按具体后端能力提供，但不是 L2 第一版必须统一的数据模型。

## 4. 工作空间与沙箱必须分离

工作空间回答“工作状态在哪里”，沙箱回答“这次执行能触达什么”。

```text
工作空间
→ 持续工作状态

执行器
→ 执行动作

沙箱 / 隔离
→ 限制执行可达范围
```

典型云端恢复流程可以是：

```text
工作空间 W1
   ↓ 挂载
沙箱 S1
   ↓ 执行
S1 退出

工作空间 W1 仍然存在
   ↓ 重新挂载
沙箱 S2
   ↓ 继续
```

本地单体实现中，工作空间和执行环境可能物理共处在一台机器上；这只是部署上的共置，不代表两者在架构语义上等价。

## 5. 执行器是 L2 的动作 primitive

执行器接受一次执行尝试，在指定环境中让它真实发生，并返回执行尝试结果：

```text
L3 动作协调器
      ↓
   执行尝试
      ↓
L2 执行器
      ↓
真实世界 / 工作空间
      ↓
执行尝试结果
```

执行器不理解计划、待办、工作流节点或模型推理。它只负责一次真实执行。

典型实现可以包括：

```text
本地 Shell 执行器
文件执行器
HTTP / API 执行器
浏览器执行器
MCP 执行器
远程任务执行器
```

工具 / 能力与执行器也必须分离：

```text
能力 / 工具
→ 语义上能做什么

执行器
→ 这次具体怎样执行
```

同一个能力可以绑定不同执行器，同一个执行器也可以承载多个能力。

## 6. 同步与异步不需要两套执行模型

短执行可以直接返回结果：

```text
execute
→ completed(result)
```

长执行可以返回一个不透明的执行引用：

```text
execute
→ pending(execution_ref)
```

之后通过状态查询、回调或外部信号确认完成。运行时可以持久化这个引用，但不解释其内部含义。

因此 L2 的核心语义支持长执行，但不要求第一版建设 Worker、消息队列或远程任务系统。

还需要保留：

> **执行器失败不等于外部执行一定失败。**

例如远程任务已经提交成功但响应丢失时，L3 仍然必须通过动作结果判定与结果核对确认真实副作用，而不能把“执行器调用超时”直接解释为动作失败。

### 6.1 执行器的恢复能力声明

执行请求至少携带逻辑动作身份、执行尝试身份、稳定幂等键、工作空间引用及当前授权范围。执行器声明以下能力是否支持及适用范围：

- 按幂等键去重，包括有效期及相同键参数不一致时的拒绝行为；
- 按执行尝试身份 / 幂等键查询，即使 `execution_ref` 尚未返回；
- 请求取消，以及取消后如何查询真实结果。

结果必须带可校验的动作 / 尝试关联和来源身份，重复、乱序或矛盾结果由 L3 依 [结果接收协议](./l3-runtime#_8-2-派发许可与结果接收) 处理。执行器不得在 L3 之外自行重试有副作用的执行。

查询应区分已完成、仍在执行、确认未执行和无法确认；临时查不到不能自动解释为未执行。取消响应也应区分请求已接收与已确认停止。

本地 Shell 或浏览器若无法提供上述保证，必须如实声明不支持；L3 将无法核对的非幂等执行保留为结果未知。接口统一不意味着所有执行器具有相同可靠性保证。

## 7. 沙箱是隔离机制，不是核心领域实体

不是所有执行都需要传统沙箱。Shell / 代码执行可能使用容器或虚拟机；浏览器使用隔离 Profile；API / MCP 可能只经过受治理代理；人工请求则没有传统意义上的沙箱。

因此：

> **沙箱是特定执行器使用的隔离承载，用于限制文件、网络、凭据、进程、计算资源及其他能力的可达范围。**

第一版可以直接使用本地进程执行；只有风险、租户隔离、远程执行或资源治理需要增强时，再引入容器、虚拟机或远程沙箱。

## 8. 观察是环境投影，不是工具结果包装

执行尝试结果回答：

> 这次物理执行返回了什么？

观察回答：

> 智能体现在应该看到什么？

例如文件写入动作的执行结果可能只是“写入成功”，但真正有决策价值的观察可能是当前 diff、语法检查、受影响文件和相关资源引用。

```text
执行结果 / 当前环境 / 外部变化
            ↓
选择 · 过滤 · 结构化 · 聚合 · 脱敏 · 引用
            ↓
           观察
```

观察应该以环境为中心，而不是以工具调用为中心。一个动作可以产生零到多个观察；用户修改文件、PR 收到新 Review、浏览器页面自行刷新等外部变化也可以形成观察。

观察不等于上下文。L2 负责形成高信号世界投影，L4 的上下文策略再决定哪些观察进入当前模型工作集。

## 9. 观察要降噪，但不能切断证据

真实环境经常产生远大于模型上下文的数据：日志、DOM、搜索结果、测试输出和 API 响应都可能很大。

因此观察的目标不是最大化原始信息量，而是：

> **最大化当前决策信号，同时保留回到原始证据的路径。**

推荐模式：

```text
高信号摘要
+
来源 / 原始结果引用
```

这样上下文可以保持紧凑，而审计、调试、复查和后续深入调查仍然可以访问原始证据。

来源与信任也不能在转换过程中丢失。来自真实 API 的结果、来自网页的不可信内容、来自另一个 Agent 的总结可以都形成观察，但其来源与信任等级并不相同。

## 10. 验证回答“世界状态是否满足明确条件”

验证不是 Agent 的主观自检，而是针对一个明确目标状态应用判定条件：

```text
目标状态
+
验证条件
+
验证方法
      ↓
验证结果
+
证据
```

例如：

- 文件是否存在；
- 代码是否能编译；
- 测试是否通过；
- JSON 是否满足 Schema；
- 数据库资源是否真实存在；
- 服务健康检查是否满足阈值。

因此：

> **Agent belief ≠ Verified fact。**

执行器可以被验证器复用，例如通过 Shell 执行测试，但“执行一个命令”和“判断一个目标状态是否成立”仍然是不同语义。

## 11. 验证、评估、验收必须分开

```text
验证
→ 当前世界状态是否满足明确条件

评估
→ 结果质量是否达到能力要求

验收
→ 业务是否接受这个结果
```

验证不一定完全确定性，例如视觉差异检查可以使用模型；真正边界不是“规则还是 LLM”，而是它是否在判断一个明确世界状态条件。

验证结果还必须能关联到它实际验证的状态。代码修改后重新改变工作空间，之前的“测试通过”不能自动证明当前状态仍然有效。第一版可以直接使用 Git commit / tree hash、内容哈希、资源版本或其他已有机制，不要求统一建设工作空间版本服务。

完成决策应尽量建立在验证证据上，而不是仅仅建立在动作执行成功上。

## 12. 安全与治理：上层决策，L2 执行边界

安全 / 治理策略可以在横切系统中定义，但真正的约束必须在最接近资源的位置执行：

```text
L5 能力
→ 描述能力需要什么权限和资源

安全 / 治理
→ 决定这次是否允许，以及允许到什么范围

L3 运行时
→ 把决策绑定到具体动作 / 执行尝试并记录生命周期

L2 工作环境
→ 真正落实文件、网络、凭据、数据和资源限制
```

核心原则：

> **只有策略判断，没有可强制执行的边界，就不构成安全保证。**

提示词中的“不要访问某目录”不是安全边界；文件系统隔离、范围受限凭据、网络代理和能力代理才是。

能力代理是 L2 中一种受治理动作出口，但不要求第一版存在独立服务。单体程序里的文件执行器、HTTP 执行器也可以直接承担约束执行角色。

## 13. 执行权限与模型可见性必须分离

系统可以被允许处理某些数据，但模型不一定应该直接看到这些数据：

```text
执行权限
≠ 模型可见性
```

例如执行器可以把大文件流式上传到批准的对象存储，而模型只看到文件引用与执行状态。

因此数据策略至少会在两个方向被落实：

```text
动作出口
→ 控制能把什么数据发送到哪里

观察入口
→ 控制哪些数据可以进入模型可见观察
```

凭据也不应该暴露给执行框架。具体凭据解析与使用发生在 L2 执行边界，并受当前授权范围约束。

## 14. 本地、持久化与分布式三个部署剖面

统一 L2 语义不意味着必须从分布式工作环境起步。

### 14.1 本地嵌入式环境

```text
单体 Python / Go 进程
│
├── 工作空间 = 本地目录
├── 执行器 = subprocess / 文件 API / HTTP client
├── 观察 = 结果适配器 / diff
└── 验证 = tests / lint / 文件检查
```

特点：单运行时协调者、本地路径、无跨节点所有权竞争、无独立服务。工作空间写入仍需按下述并发准入规则协调。

### 14.2 单节点持久化环境

```text
运行时进程 / Pod
    │
    ▼
持久工作空间
    │
    ▼
本地 / 远程执行器
```

关键变化不是“上云”，而是必须假设执行承载可能重启、迁移或被回收：

```text
Sandbox dies
→ Workspace survives
```

因此工作空间需要独立持久化；执行器可以仍然位于同一进程，也可以访问远程沙箱或任务系统。

### 14.3 共享工作空间的本地并发约束

策略上没有顺序依赖，不代表动作不会修改同一资源。单进程内的多个执行尝试也可能覆盖文件或污染验证结果。

第一版对同一工作空间的写操作串行执行；访问范围不明的 Shell / 程序执行按独占写处理。用于完成门禁的验证必须针对隔离快照，或在整个验证期间阻止该工作空间写入，并记录实际验证的版本。普通读取若允许与写入并发，不能被当作一致快照证据。

L3 持久管理尝试、派发许可及资源占用引用，L2 负责实际资源准入、隔离及互斥执行。占用必须在真实执行前持久关联到尝试；若准入结果未知则禁止派发并先核对，不能在崩溃后丢失占用。只有具有隔离工作副本或可证明资源互不冲突时才并行写入。对外部用户或工具的修改，内部互斥并不充分；应使用快照 / 版本校验，无法确认稳定目标时拒绝生成有效的完成证据。

重启后必须先处理仍可能存活的本地进程或远端执行，再释放资源占用并派发冲突动作；不能把运行时进程退出视为执行已经停止。若执行器不支持查询，或无法确认旧执行已终止，相关资源必须保持持久阻塞，拒绝新的冲突执行，不因超时、租约到期或协调者重启自动释放。进入显式干预或执行器特定的恢复流程，只有取得旧执行已停止，或其写权限已被资源侧可靠撤销的证据后才能解除阻塞。仅标记阻塞并不能阻止旧进程写入；隔离令牌只有在资源实际校验并拒绝旧令牌时才构成隔离保证。数据库 / SaaS 等不由工作空间锁保护的资源，使用对应执行器和目标系统的并发控制。

### 14.4 分布式 / 协作环境

在本地互斥之外，出现多 Worker、多 Agent 或跨节点共享工作状态时，可以额外增加：

```text
Workspace locator
Resource identity / version
Ownership / Lease
Conflict detection
Branch / Merge
Worker routing / placement
Dispatch deduplication
Capacity / backpressure
```

这些机制的分布式实现属于部署剖面的增强；持久派发去重和共享资源互斥仍需在单节点恢复与并发场景中落实。

## 15. 第一版最小实现

第一版 Agent Platform 可以非常简单：

```text
Python / Go Process
│
├── L4 Harness
├── L3 Runtime
└── L2 Work Environment
    ├── Workspace = /work/project
    ├── FileExecutor
    ├── ShellExecutor
    ├── ObservationAdapter
    └── Verifier
```

也就是说：

```text
Workspace
→ directory

Executor
→ function / subprocess

Observation
→ struct / text + refs

Verification
→ deterministic checks
```

这些已经足以实现完整的 L2 语义。之后可以逐步替换成持久卷、远程沙箱、浏览器服务、任务 Worker、能力代理或分布式工作空间，而不改变核心模型。

## 16. 核心不变量

1. **工作环境不等于沙箱；沙箱只是执行隔离机制之一。**
2. **工作空间保存工作状态，执行器执行动作，两者生命周期必须解耦。**
3. **工作空间生命周期不等于运行生命周期，也不等于沙箱生命周期。**
4. **工作空间内容属于 L2 世界状态；L3 执行检查点只保存必要引用，不复制整个工作世界。**
5. **工具 / 能力描述“能做什么”，执行器描述“这次怎样执行”。**
6. **执行器失败不等于外部执行一定失败；可靠性最终由 L3 动作判定语义收敛。**
7. **观察是面向智能体的环境投影，不是工具结果包装，也不等于模型上下文。**
8. **观察应保留来源和原始证据引用，信息转换不会自动提升信任。**
9. **Agent 主观判断不等于验证事实；验证必须针对明确目标状态并产生可追溯证据。**
10. **验证、评估、验收分别回答世界状态、能力质量和业务接受三个不同问题。**
11. **安全 / 治理决定边界，L2 在最接近资源的位置真正执行边界。**
12. **执行权限不等于模型可见性；允许处理数据不代表允许把数据暴露给模型。**
13. **本地目录、subprocess 和文件 API 就是合法的第一版 L2 实现；分布式机制不是核心语义。**
14. **逻辑组件边界不等于物理服务边界。**
