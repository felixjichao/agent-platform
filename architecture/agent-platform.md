# 智能体平台总体架构

本文档是 Agent Platform 当前的规范性架构文档。文章目录保存研究过程和依据；本文件只保留已经形成的稳定架构结论，并通过 Git 历史记录这些结论如何逐步演进。

## 1. 总体架构主张

Agent Platform 的目标，不是为每一种智能体产品形态实现一套独立框架，而是为**动态组装、非确定、长期运行、可并行、可编程的智能执行过程**提供一套稳定的生产系统边界。

平台最终需要把这样的执行过程约束在：

> **持久、可恢复、可验证、可观测、可治理、可持续演进的系统中。**

统一心智模型：

```text
业务目标
   ↓
能力契约
   ↓
动态组装能力
   ↓
选择执行策略 / 执行框架
   ↓
统一运行时记录真实执行
   ↓
智能体工作环境执行动作、处理数据、提供反馈
   ↓
真实世界
```

同时，上下文 / 记忆、评估 / 追踪、安全与治理贯穿整个软件栈。

## 3. 每一层回答什么问题

### L7 业务 / 产品：要完成什么？

负责：

- 目标；
- 项目；
- 业务任务；
- 用户价值；
- 业务约束和责任。

对话、科研助手、知识库、编程助手、工作流产品等都属于应用形态，不等于执行范式。

### L6 能力契约：什么叫“具备这项能力”？

负责定义：

```text
能力
├── 目标 / 需求
├── 验收标准
├── 质量标准
├── 评估契约
└── 证据要求
```

执行框架描述“怎么实现”，评估描述“怎么证明”。

### L5 能力工程：智能体能学什么、能做什么？

负责组织：

- 技能（Skill）：程序性知识；
- 工具（Tool）：行动能力；
- MCP / API 绑定：连接实现；
- 能力发现；
- 能力适配器；
- 能力修订版本 / 评估。

### L4 执行策略：当前任务怎么推进？

负责：

- 直接执行；
- 工作流；
- 智能体循环；
- PTC；
- 多智能体；
- 规划；
- 委派；
- 上下文策略；
- 评估策略；
- 自主策略；
- 完成策略 / 升级策略；
- 控制权转移策略。

这些策略主要由执行框架（Harness）承载。

### L3 统一运行时：实际上发生了什么？

负责记录和管理执行事实、状态、生命周期、恢复和因果关系，不负责把某一种执行框架策略固化为系统唯一执行方式。

### L2 智能体工作环境：智能体能观察和作用于什么世界？

负责：

- 工作空间；
- 数据与动作执行；
- 工作发现；
- 共享状态；
- 所有权；
- 观察；
- 验证；
- 沙箱 / 隔离；
- 能力代理；
- 程序化执行。

### L1 基础设施 / 真实世界：真正的资源在哪里？

包括 API、SaaS、数据库、浏览器、文件、计算资源、网络、设备等。

## 4. 核心设计原则

### 4.1 应用形态不等于执行范式

```text
应用形态
对话 · 科研 · 知识库 · 编程助手 · 行业应用

执行范式
直接执行 · 工作流 · 智能体 · PTC · 多智能体
```

同一种产品可以使用不同执行策略，同一种执行策略也可以服务多个产品。

### 4.2 工作流与智能体的真正区别是执行控制权

```text
工作流
→ 下一步主要由预定义代码 / 图决定

智能体
→ 下一步主要由模型基于上下文动态决定
```

因此：

> **静态工作流 → 动态工作流 / 计划 → 智能体循环，是一条连续谱。**

工作流图是输入表达；智能体图更接近运行时结果。

### 4.3 运行时稳定，执行框架可替换

执行框架编码了“当前模型还做不到什么”的假设。

这些假设会随着模型升级而过时，所以：

> **运行时应保持稳定；执行框架应可替换、可简化，甚至可以被移除。**

规划器、评估器、初始化器、上下文重置、待办、完成策略等默认属于执行框架，而不是运行时核心。

### 4.4 长期工作连续性不依赖智能体连续性

> **智能体可以忘记、退出或被替换；工作必须记住。**

长任务依赖持久工作状态、工作空间、事件、制品、交接和恢复，而不是一个会话永久不结束。

### 4.5 LLM 应是控制面，而不是数据面

模型适合做高价值、不确定决策；数据搬运、循环、关联、过滤、聚合和稳定机制尽量进入执行环境。

```text
智能体 / 执行框架
= 执行控制面

智能体工作环境
= 数据面 + 动作面
```

### 4.6 执行、验证、验收、发布相互分离

```text
已执行
≠ 已验证
≠ 已验收
≠ 已发布 / 已部署
```

智能体认为完成，不代表系统验证通过；验证通过，也不自动等于业务接受或允许生产发布。

### 4.7 自主性是部署特征，不是执行范式

自主性（Autonomy）描述真实部署中，智能体在多大程度上可以独立于人工直接指导和监督做出执行决策。它不是模型的固定属性，也不等于某一种执行范式。

```text
模型能力 + 执行框架
      ↓
   潜在自主性
      ↓ 受权限 / 风险 / 产品策略 / 人工监督约束
   实际自主性
```

直接执行、工作流、智能体循环、PTC、多智能体回答“任务怎么推进”；自主性回答“推进过程中，系统允许智能体自己决定多少”。

> **生产系统不应最大化自主性，而应在可验证、可观察、可干预的边界内最大化有用的自主性。**

## 5. 核心领域模型

以下中文名称对应正式代码模型 `Work / Session / Run / Event / Action / Result / Observation / Artifact`；正文优先使用中文，Schema、事件名和代码类型保持英文。

### 5.1 工作（Work）

工作是长期目标和共享工作世界的载体：

```text
工作 / 项目
├── 目标
├── 能力 / 验收契约
├── 共享资源
├── 工作前沿
├── 制品
├── 环境 / 工作空间
├── 长期进度
└── 会话
```

多个智能体、多个会话、多个执行框架修订版本可以围绕同一个工作协作。

### 5.2 会话（Session）

会话表示：

> **一个智能体与一个工作之间相对连续的认知 / 执行关系。**

会话不是聊天历史，也不是上下文窗口。

同一个工作可以：

- 顺序经历多个会话；
- 并行存在多个会话；
- 智能体更换后继续存在。

### 5.3 运行（Run）

运行表示：

> **运行时被触发后，在一个会话内发生的一次连续执行片段。**

常见的新运行触发：

- 用户消息；
- 人工批准 / 输入；
- 定时器 / Webhook；
- 外部事件；
- 子会话完成。

基础设施内部恢复通常仍属于同一个运行，例如 worker restart、tool retry。

### 5.4 事件（Event）

事件是已经发生的事实，是持久执行历史的重要基础。

典型类别如下。事件类型是代码标识，因此保持英文：

```text
触发器
├── UserMessageReceived
├── ExternalEventReceived
└── TimerTriggered

运行
├── RunStarted
├── RunPaused
├── RunCompleted
└── RunFailed

动作
├── ActionRequested
├── ActionStarted
├── ActionSucceeded
└── ActionFailed

人工交互
├── ApprovalRequested
├── ApprovalGranted
├── ApprovalRejected
└── HumanInputReceived

制品
├── ArtifactCreated
└── ArtifactUpdated

恢复
├── RecoveryStarted
└── RecoveryCompleted
```

规划事件默认不属于运行时核心，因为计划属于执行框架策略。

推荐事件信封（Event Envelope）：

```text
event_id
event_type
schema_version
work_id
session_id
run_id
sequence
timestamp
actor
causation_id
correlation_id
payload
```

### 5.5 命令、事件、状态

```text
命令
→ 希望发生什么

事件
→ 实际发生了什么

状态
→ 根据事实得到的当前视图
```

推荐：

```text
动作 / 结果
    ↓
   事件
    ↓ 追加
 事件日志
    ↓ 投影
   状态
```

状态可以被重建；事件日志承担持久事实源。快照是恢复优化，不是事实源。

### 5.6 动作（Action）

动作是运行时向执行环境发出的受治理执行请求。

来源可能是工作流、执行框架、程序、人或系统自动机制。

### 5.7 结果（Result）

结果是动作的真实执行结果，属于执行事实。

### 5.8 观察（Observation）

观察是从结果、资源或环境中构建出的面向模型投影：

```text
动作
 ↓
原始结果
 ↓
过滤 / 转换 / 聚合 / 脱敏 / 持久化
 ↓
观察
 ↓
上下文
```

> **结果是执行事实；观察是面向模型的投影。**

### 5.9 制品（Artifact）

制品是正式结果 / 交付物，具有版本、评审、发布或引用语义。

它与笔记的区别：笔记是智能体当前主观认知；制品是正式工作产物。

### 5.10 控制权转移

人工中断、纠偏、智能体主动请求澄清、风险边界触发升级等，都是实际发生的执行事实，应由运行时记录，而不是只存在于聊天文本中。

执行框架负责判断何时继续自治、何时交还控制权；运行时负责提供确定性的暂停、恢复、中断、取消和重定向能力，并记录相应事实。

```text
人委托控制权
   ↓
智能体自主执行
   ↓ 不确定性 / 信息缺失 / 能力缺口 / 风险边界
控制权转移
   ↓
人工决策 / 纠偏 / 补充信息
   ↓
继续执行或终止
```

## 6. 上下文、记忆、工作空间

### 6.1 会话 ≠ 状态 ≠ 上下文

```text
会话
→ 持久执行历史

状态
→ 当前运行视图

上下文
→ 当前模型工作集
```

上下文是投影，可以丢弃和重建。

### 6.2 上下文构建器

```text
会话
状态
记忆
笔记
制品
工作空间
技能
能力
外部资源
    ↓
上下文构建器
    ↓
  上下文
```

上下文构建器属于执行框架中的上下文策略。

### 6.3 上下文是工作集

> **上下文包含的是地图，而不是整个世界。**

稳定内容适合前置：

- 系统规则 / 策略；
- 智能体定义；
- 能力元数据。

阶段性稳定：

- 目标；
- 检查点；
- 摘要；
- 当前计划。

动态内容：

- 最近历史；
- 观察；
- 即时知识；
- 工具 / 技能细节。

### 6.4 上下文压缩

```text
会话追加事实
      ↓
上下文策略
      ↓
选择 / 摘要 / 压缩
      ↓
上下文
```

压缩改变模型看到什么，不改变真实发生过什么。

### 6.5 笔记 / 待办

智能体当前主观工作认知，包括计划、待办、假设和临时结论。

它可以被修改，也可能是错的，因此不是事实源。

### 6.6 记忆（Memory）

可以区分：

- 工作记忆 → 笔记 / 待办；
- 情景记忆 → 过去任务 / 会话经验；
- 语义记忆 → 稳定知识、规则、偏好。

长期记忆推荐采用晋升流程：

```text
会话 / 观察
     ↓
候选记忆
     ↓
验证 / 来源 / 信任
     ↓
长期记忆
```

原则：

> **可以自由写入候选，但必须谨慎晋升为长期记忆。**

召回不能只用向量 Top-K，还应考虑目标、状态、范围、时效性、重要性、置信度、信任与来源。

### 6.7 工作空间（Workspace）

工作空间是工作的外部持久工作状态：

- 文件；
- 代码；
- 中间数据；
- 检查点；
- 生成程序；
- 进度。

工作空间不等于记忆，也不属于单个上下文。

## 7. 能力工程

### 7.1 能力分类

```text
能力
├── 程序性能力
│   └── 技能
│
└── 行动能力
    └── 工具
```

### 7.2 工具、技能、MCP、执行框架

```text
工具
→ 能做什么动作

技能
→ 这类任务通常应该怎么做

MCP
→ 如何连接外部系统

执行框架
→ 当前任务现在怎么推进
```

### 7.3 能力适配器

```text
后端 API / MCP 工具
        ↓
能力适配器
        ↓
面向智能体的工具
```

API 原子性不等于面向智能体的能力粒度。

### 7.4 智能体决策边界

> **确定性机制下沉到能力；不确定决策留给执行框架。**

工具太原子会产生大量无意义编排；工具太大则会把真正需要智能体判断的策略藏进黑盒工作流。

### 7.5 能力目录与分类体系

```text
领域
 ↓
资源
 ↓
语义能力
 ↓
具体技能 / 工具
```

每个能力要明确“做什么”“什么时候用”“什么时候不用”以及边界和相邻能力。

### 7.6 能力发现 ≠ 能力加载

能力规模化后：

```text
能力发现
   ↓
元数据
   ↓
选择
   ↓
技能 / 工具细节加载
```

不要永久把全量工具 / 技能定义放入上下文。

### 7.7 技能渐进披露

```text
技能元数据
    ↓
SKILL.md
    ↓
参考资料 / 脚本 / 资源
```

技能是可发现、可导航、按需加载的程序性知识。

### 7.8 技能脚本与工具

技能内部脚本服务于某个技能的稳定局部实现；工具是平台级、可治理、可复用的行动能力。

不是每个脚本都需要注册成全局工具。

### 7.9 MCP 的位置

> **MCP 是连接标准，不是能力设计标准。**

推荐：

```text
技能
 ↓ 依赖
语义能力
 ↓ 绑定
工具
 ↓ 通过以下方式实现
MCP / API / 本地脚本
```

### 7.10 工具契约

```text
工具契约
├── 身份
├── 适用范围
├── 语义
├── 输入 / 输出 Schema
├── 使用指导
├── 副作用
└── 权限 / 风险
```

Schema 描述机器允许什么；使用指导帮助智能体正确选择和使用。

### 7.11 动态组装智能体

```text
基础智能体
+ 选中的技能
+ 选中的工具
+ 召回的知识
+ 任务上下文
       ↓
实际工作的智能体
```

> **智能体使用能力，但不拥有能力。**

能力资产应独立、可版本化、可发现、可组合、可治理。

### 7.12 评估驱动的能力工程

工具和技能都从真实能力缺口出发，通过试验、追踪、评估持续迭代。

工具使用异味包括：错误工具切换、重复重试、结果过大、参数无效等。

技能失败包括：发现失败、错误激活、导航失败、指令失败、上下文过载、过程失败。

## 8. 执行策略

### 8.1 直接执行

模型直接做一次决策或直接调用少量工具。

### 8.2 工作流

代码拥有主要执行控制权。

基础控制原语：

- 顺序；
- 分支；
- 分叉 / 汇合；
- 循环；
- 动态展开。

### 8.3 智能体循环

模型持续根据上下文和观察决定下一动作。

### 8.4 PTC

PTC（Programmatic Tool Calling，程序化工具调用）是工具编排模式，不是工具类型。

```text
模型
 ↓ 生成程序
程序
 ├── 工具 A
 ├── 工具 B
 ├── 循环
 ├── 过滤
 └── 聚合
      ↓
观察
 ↓
模型
```

一个推理步骤可以对应许多环境动作。

### 8.5 多智能体

使用多智能体取决于：

```text
价值
≈ 可并行性
 + 上下文独立性
 + 结果可合并性
 - 依赖密度
 - 协调成本
```

复杂任务本身不是理由。

### 8.6 自主策略与执行策略正交

工作流、多智能体或智能体循环本身不能说明系统的自主程度。同一执行范式可以在不同权限、风险和人工监督配置下表现出完全不同的实际自主性。

自主策略应由执行框架结合任务风险、可逆性、验证能力、权限范围和人工监督能力动态决定，而不是作为产品或模型的固定等级。

## 9. 多智能体架构

### 9.1 主智能体（Lead Agent）

> **主智能体 = 编排者 + 全局上下文负责人。**

负责全局目标、工作拆解、委托、覆盖度、冲突和最终综合。

### 9.2 智能体即工具 vs 子会话

智能体即工具：聚焦短调用，是父会话中的一次动作。

自治子智能体：拥有独立目标、多轮上下文、制品和恢复能力，需要独立子会话。

### 9.3 动态团队形成

```text
目标
+ 能力
+ 知识
+ 权限
+ 预算
+ 风险
   ↓
执行框架
   ↓
单智能体 / 工作流 / 多智能体 / 混合模式
```

智能体团队本身可以是运行时结果。

### 9.4 工作前沿

工作前沿是当前独立、可领取、可验证的工作项集合。

> **有效并行度约等于独立工作前沿的数量。**

多智能体的关键是工作调度器，而不是智能体调度器。

### 9.5 共享状态 + 局部隔离

共享世界协作需要：

- 共享资源；
- 本地工作空间；
- 资源身份 / 版本；
- 所有权 / 租约；
- 快照 / 变化；
- 冲突处理。

协作可以通过环境状态发生，不必全部依赖智能体之间直接传消息。

### 9.6 局部恢复 + 全局协调

子任务局部失败优先局部恢复；结果回到父级重新协调全局计划。

### 9.7 两层并发

- 委派并发；
- 动作 / 工具并发。

两层拥有独立预算和背压策略。

### 9.8 信任感知的智能体交接

智能体之间的结果不应该只是一段文本：

```text
智能体消息 / 委派结果
├── semantic_type
├── content
├── provenance
├── evidence_refs
├── confidence
└── trust_label
```

信息经过转换不会自动提升信任等级。

## 10. 智能体工作环境

```text
智能体工作环境
├── 共享资源
├── 本地工作空间
├── 程序化执行运行时
├── 工作发现
├── 所有权 / 租约
├── 观察投影
├── 验证
├── 反馈 / 判定器
├── 能力代理
├── 沙箱 / 隔离
└── 遥测通道
```

### 10.1 环境工程

原始结果需要转换成高信号观察，而不是把原始日志和 API 响应全部塞给模型。

### 10.2 程序化执行运行时

```text
程序化执行运行时
├── 沙箱 / 隔离
├── 工作空间
├── 能力代理
├── 权限策略
├── 数据流策略
├── 资源预算
├── 凭据隔离
├── 动作追踪
├── 终止 / 超时
└── 恢复
```

允许执行代码不等于允许调用任意业务能力。

### 10.3 程序预算

治理项包括：`max_tool_calls`、`max_runtime`、`max_cost`、`max_parallelism`、CPU / 内存、数据读 / 写等。

### 10.4 生成代码生命周期

```text
临时代码
→ 运行范围

工作空间代码
→ 工作范围

晋升后的能力
→ 跨工作的平台资产
```

晋升为共享能力前必须经过评估、安全检查、评审和版本管理。

### 10.5 工作环境同时服务执行、验证和监督

可安全授予的自主空间高度依赖工作环境是否隔离、可逆、可验证、可观察。工作环境不只是智能体执行动作的地方，也应为机器验证和人工监督提供稳定的事实与控制接口。

## 11. 数据面

### 11.1 数据可见性

```text
模型可见数据
仅执行环境可见数据
持久资源
```

智能体系统可以被允许处理某些数据，而模型不被允许直接看到这些数据。

### 11.2 数据流策略

```text
来源
+ 数据分类
+ 目的地
+ 能力
+ 主体 / 租户
+ 用途 / 工作上下文
      ↓
允许 / 拒绝 / 脱敏
```

能力权限与数据流权限不是同一个维度。

## 12. 评估架构

### 12.1 试验（Trial）是基本单位

```text
评估套件
   └── 任务
        └── 试验
             ├── 执行框架修订版本
             ├── 能力修订版本
             ├── 环境修订版本
             ├── 过程记录 / 追踪
             ├── 最终结果
             └── 评分结果
```

### 12.2 过程记录 / 追踪与最终结果

追踪描述过程发生了什么；最终结果描述执行后真实世界和结果是什么。

二者必须分离。

### 12.3 评估契约

```text
评估契约
├── 评估标准
├── 证据来源
├── 评分器
├── 阈值 / 关键程度
└── 聚合方式
```

### 12.4 评分器

- 确定性评分器；
- LLM 评分器；
- 人工评分。

评估标准、证据和评分器分开建模。

### 12.5 非确定性

- pass@k：至少一次成功，更接近能力上限 / 搜索潜力；
- pass^k：全部成功，更接近可靠性。

### 12.6 能力评估与回归评估

能力评估探索能力边界；成功案例逐渐晋升到回归套件，守住已有能力。

### 12.7 评估基础设施与评估内容

平台负责运行器、环境、追踪、评分器 SDK、统计、版本管理。

领域 / 能力负责人负责任务、标准、评分规则、参考解法、失败案例、领域评分器。

> **评估基础设施是平台能力；评估内容是能力资产。**

### 12.8 评估是能力规格

```text
执行框架
→ 如何实现

评估
→ 如何证明
```

### 12.9 上线前评估与部署评估

上线前评估回答“在受控条件下能不能做到”；部署后监控与部署评估回答“在真实用户、真实权限和真实任务下实际上如何运行”。

```text
能力定义
   ↓
上线前评估
   ↓
发布 / 部署
   ↓
部署后监控
   ↓
真实行为 / 失败模式
   ↓
形成新的评估任务
   ↓
回归评估
   ↓
执行框架 / 能力修订
```

生产失败不应止于修复单个问题，而应尽量沉淀为可重复的评估任务和回归用例。

## 13. 验证架构

### 13.1 验证阶梯

```text
本地检查
   ↓
回归验证
   ↓
代表性工作负载
   ↓
集成验证
   ↓
类生产环境验证
```

### 13.2 差异判定器

验证器应尽量告诉智能体“差在哪里、下一步如何定位”，而不仅是通过 / 失败。

### 13.3 质量守护者

维护跨工作项的长期质量维度，例如回归、架构约束、技术债和共享资源健康。

### 13.4 单次成功结果成本

最终成本指标关注“一个成功结果需要多少总资源”，而不是单次 token / request 价格。

## 14. 安全与治理

安全目标可以理解为：

```text
部署风险
≈ 失败概率 × 影响半径
```

模型 / 分类器 / HITL 主要降低失败概率；隔离控制负责限制最大影响半径。

### 14.1 三类风险来源

```text
用户误用
模型错误行为
外部攻击 / 提示词注入
```

因此需要纵深防御：

```text
行为安全
内容安全
环境安全
```

### 14.2 上下文入口边界

外部内容进入上下文前经过：

```text
原始内容
   ↓
来源信息
信任分类
提示词注入检测
数据检查
脱敏 / 清洗
策略
   ↓
观察
   ↓
上下文
```

可信工具不等于可信工具输出。

### 14.3 信任生命周期

```text
已发现
  ↓
不可信
  ↓
可信读取
  ↓
可信指令
  ↓
可信执行
```

本地性不等于可信。

对于智能体，“读”本身可能影响行为，因此信任边界需要覆盖解析、加载和解释。

### 14.4 信任传播

信任跟随数据来源传播，而不是因为信息经过内部智能体就自动升级。

```text
信息转换
≠ 信任提升
```

### 14.5 智能体身份

推荐身份链：

```text
人类主体
   ↓ 委派
智能体主体
   ↓ 收窄权限
执行主体
   ↓ 使用
范围受限的凭据
```

区分：

```text
身份 → 我是谁
委派 → 我代表谁
权限 → 我能做什么
凭据 → 我如何证明权限
```

### 14.6 授权模型

核心授权单元：

```text
主体
× 委派链
× 能力
× 资源
× 范围
× 时长
× 工作上下文
```

委派传递目标，不默认复制权限。

### 14.7 即时能力授权

权限按工作 / 阶段动态收缩：

```text
任务需要
  ↓
能力请求
  ↓
策略
  ↓
临时范围授权
  ↓
执行
  ↓
撤销 / 收窄
```

最小权限进一步扩展为：

```text
最小权限
× 最短时长
× 最小范围
```

### 14.8 隔离控制 = 可达范围控制

隔离控制不只是 `sandbox=true`，而是控制当前智能体可触达的世界：

```text
智能体可达范围
├── 文件系统
├── 网络
├── 凭据
├── 能力
├── 数据
├── 记忆
├── 其他智能体
└── 外部系统
```

目标是让每个工作 / 运行 / 子智能体的可达图尽可能小。

### 14.9 隔离配置

```text
隔离配置
├── isolation_mode
├── filesystem_scope
├── network_scope
├── credential_scope
├── resource_budget
├── allowed_capabilities
├── approval_boundary
└── user_oversight_level
```

隔离强度需要匹配风险、自主程度和用户监督能力。

### 14.10 出站治理

域名白名单不够：一个域名可能承载大量不同能力和租户。

```text
出站治理
├── 目的地
├── 协议
├── 能力
├── 凭据
├── 租户 / 主体
├── 数据分类
└── 来源信息
```

> **允许访问某个域，本质上是一组能力授权，而不是简单的目的地过滤。**

### 14.11 记忆治理

长期记忆写入近似于修改未来智能体的启动上下文，因此需要：

- 来源信息；
- 信任；
- 晋升；
- 验证；
- 启动扫描；
- 信任感知召回。

不可信内容被智能体总结后，不能自动变成高可信记忆。

### 14.12 用户意图与能力边界

来自用户的指令也可能由攻击者诱导产生。

```text
指令来源
≠ 意图来源
```

用户意图定义目标，但系统能力边界独立存在。

HITL 不应该承担用户根本无法理解的底层安全决策。

### 14.13 隔离与可观测性

强隔离可能降低宿主机可见性，因此需要带外遥测通道。

```text
治理
= 策略
+ 执行约束
+ 可观测性
```

### 14.14 经验证的基础原语

智能体特有创新优先放在治理 / 策略组合；隔离 / 约束执行尽量复用成熟基础设施：

- Hypervisor；
- OS 沙箱；
- seccomp / namespace；
- 文件系统 ACL；
- firewall / proxy；
- IAM / 范围受限凭据；
- 资源限制。

> **治理决定边界画在哪里；成熟基础设施保证智能体越不过这条边界。**

### 14.15 自主性与风险联合治理

自主性与风险是两个正交维度。高自主并不自动意味着高风险，低自主动作也可能因为资源范围或后果不可逆而具有高风险。

```text
自主空间
受以下因素共同约束：
风险 × 可逆性 × 可达范围 × 验证能力 × 人工监督能力
```

更成熟的策略是在动作级动态决定控制权：低风险、可逆、可验证区域可以自动执行；高风险边界触发人工监督、升级或确定性拒绝。

> **隔离控制决定最多能触达到哪里；自主策略决定在这个边界内可以自己决定多少。**

## 15. 可观测性与追踪

### 15.1 智能体追踪

用于理解智能体为什么这么做：

- 模型步骤；
- 工具选择；
- 委派；
- 评估；
- 最终结果。

### 15.2 运行时追踪

围绕工作、会话、运行、事件、动作记录完整执行关系。

### 15.3 安全追踪

来自更接近约束执行的位置：

- 进程启动；
- 文件系统访问；
- 网络出站；
- 凭据使用；
- 策略决策；
- 沙箱违规。

智能体追踪与安全追踪可以通过 `work_id`、`session_id`、`run_id`、`action_id`、`correlation_id` 关联，但不应完全依赖同一个采集机制。

### 15.4 PTC 追踪

层级关系：

```text
推理步骤
  ↓
程序
  ├── 动作 A
  ├── 动作 B
  ├── 动作 C
  └── 策略决策
```

不能只记录 `CodeExecutionSucceeded`。

### 15.5 自主性遥测

自主性不是运行时事实字段，而是基于运行、动作和控制权转移事实形成的测量投影：

```text
运行 / 动作 / 控制权转移事件
              ↓
          自主性投影
              ↓
连续自主时长 · 人工干预 · 主动升级 · 自主完成率 · 风险分布
```

自主性指标必须与最终结果、验证通过率和风险联合解释，不能单独优化“运行更久”或“减少人工介入”。

### 15.6 部署后监控

真正理解智能体行为需要工作、会话、运行级的执行关联，而不能只记录单次模型请求或工具调用。

部署后监控应在隐私保护前提下记录足够的结构化事实，例如控制权转移、策略决策、动作元数据、结果和验证状态，并将真实失败模式反哺回归评估。

## 16. 恢复与升级

### 恢复

解决当前能力范围内的暂时故障：

- worker restart；
- 执行框架崩溃；
- 临时工具故障；
- 可重试动作失败。

### 升级

解决能力边界：

- 更强模型；
- 专项能力；
- 人工决策；
- 新工具；
- 缩小范围。

> **恢复解决暂时失败；升级解决能力上限。**

升级也承担控制权交还职责：当不确定性、信息缺失、权限或风险超过当前自主边界时，执行框架应主动升级，而不是持续猜测或无界重试。

## 17. 执行框架工程

执行框架是持续实验对象：

```text
执行框架修订版本
      ↓
     试验
      ↓
追踪 + 最终结果
      ↓
     评估
      ↓
   失败分析
      ↓
执行框架修订版本
```

执行框架修订版本、技能修订版本、工具修订版本、评分器修订版本都应该被版本化。

执行框架发布不等于正在执行的会话自动迁移。

## 18. 能力生命周期

系统中的可复用能力应该经过明确生命周期：

```text
能力缺口
   ↓
候选
   ↓
原型
   ↓
能力评估
   ↓
安全 / 治理评审
   ↓
发布修订版本
   ↓
回归评估
   ↓
生产反馈
   ↓
修订 / 废弃
```

对于生成代码：

```text
临时代码
→ 工作空间代码
→ 候选能力
→ 评估 / 评审
→ 技能 / 工具 / 其他可复用能力
```

智能体可以提出候选能力，但不能在活跃生产会话中无治理地自行发布。

## 19. 人类治理与监督

### 19.1 人类治理面

随着智能体自主性增强，人类角色从：

```text
逐步指导执行路径
```

转向：

```text
治理面
├── 目标
├── 能力 / 验收
├── 风险边界
├── 预算
├── 升级
├── 生产验收
└── 发布 / 部署决策
```

HITL 仍然重要，但它应主要承担人类有能力做出的语义决策，而不是替代沙箱、凭据隔离、出站策略等系统硬边界。

### 19.2 人工监督面

人工监督面关注运行过程中，人如何保持态势感知并在需要时改变执行轨迹：

```text
人工监督面
├── 进度投影
├── 风险可见性
├── 动作 / 计划可见性
├── 暂停 / 恢复
├── 中断
├── 纠偏 / 实时引导
├── 审批
├── 评审
├── 验收
└── 升级
```

人工监督面与人类治理面语义不同：治理面决定目标、边界、预算和最终验收；监督面负责执行过程中如何观察、介入和纠偏。

有效监督的判断标准不是“是否对每个动作审批”，而是人是否真正处于能够看清状态、理解风险并及时介入的位置。

## 20. 核心架构不变量

1. **应用形态不等于执行范式。**
2. **工作流与智能体的核心区别是执行控制权归属。**
3. **运行时管理执行事实，执行框架管理执行策略，业务层管理工作意图。**
4. **运行时应稳定，执行框架应可替换、可简化甚至消失。**
5. **工作是长期连续性的载体；智能体、会话、上下文都可以被替换或重建。**
6. **工作、会话、运行分别表示长期工作、智能体与工作的连续关系、一次触发后的连续执行片段。**
7. **事件是事实，状态是投影，快照是优化。**
8. **上下文是工作集和查询投影，不是事实源。**
9. **上下文压缩改变模型看到什么，不改变真实历史。**
10. **笔记是主观工作认知，记忆是跨时间保留信息，工作空间是外部工作状态，制品是正式产物。**
11. **工具是行动能力，技能是程序性知识，MCP 是连接标准，执行框架是当前执行策略。**
12. **智能体可以由基础智能体 + 技能 + 工具 + 知识 + 任务上下文动态组装。**
13. **能力发现与能力加载必须分离。**
14. **确定性机制下沉到能力，不确定决策留给执行框架。**
15. **结果是执行事实，观察是面向模型的投影。**
16. **LLM 应是控制面，而不是数据面。**
17. **PTC 是执行策略，不是工具类型；一个推理步骤可以展开多个受治理动作。**
18. **代码执行权限不等于业务能力权限。**
19. **多智能体的关键不是智能体数量，而是工作前沿和共享工作环境。**
20. **主智能体负责全局编排和全局上下文；子会话负责局部自治工作。**
21. **委派传递目标，不默认复制权限。**
22. **试验是智能体评估的基本单位；过程记录 / 追踪与最终结果分离。**
23. **最终结果是事实，评估分数是测量投影。**
24. **评估是可执行的能力规格：执行框架说明怎么实现，评估说明怎么证明。**
25. **能力评估探索能力边界，回归评估守住已获得能力。**
26. **执行、验证、验收和发布 / 部署状态必须分离。**
27. **智能体安全同时治理上下文入口、信任传播、执行边界和出站。**
28. **可信能力不代表可信观察。**
29. **信任跟随来源信息传播，不因经过内部智能体或智能体摘要自动升级。**
30. **用户意图可以定义目标，但不能自动扩大能力边界。**
31. **智能体应成为可独立授权、审计和撤销的主体，同时保留人类委派链。**
32. **隔离控制的本质是可达范围控制：让智能体可达世界保持任务所需最小范围。**
33. **最小权限还要结合最短时长与最小范围。**
34. **概率型防御降低失败概率，确定性隔离限制最大后果。**
35. **治理定义边界；成熟基础设施执行边界。**
36. **治理 = 策略 + 约束执行 + 可观测性。**
37. **人类应逐渐从执行路径移向目标、风险、验收和升级所在的治理面。**
38. **自主性不是模型或执行范式的固定属性，而是模型、执行框架、权限、产品设计和人工监督共同形成的部署特征。**
39. **执行策略回答任务怎么推进；自主策略回答在既定边界内智能体可以自己决定多少。**
40. **控制权转移是执行事实，自主性指标是基于这些事实形成的测量投影。**
41. **自主性必须与风险、可逆性、可达范围和验证能力联合治理，而不能被单独最大化。**
42. **有效人工监督不等于逐步审批，而是能够持续观察，并在需要时中断、纠偏、升级或验收。**
43. **上线前评估测能力潜力，部署后监控测真实行为；生产反馈应持续反哺回归评估。**

## 21. 一句话总结

> **Agent Platform 的核心，不是“跑一个智能体循环”，而是把一个动态组装、非确定、长期、并行、可编程的智能执行过程，约束在持久、可恢复、可验证、可观测、可治理、能够持续演进的生产系统中。**
