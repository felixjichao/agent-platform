# 智能体平台总体架构

本文档是 Agent Platform 当前的规范性架构文档。文章目录保存研究过程和依据；本文件只保留已经形成的稳定架构结论，并通过 Git 历史记录这些结论如何逐步演进。

## 1. 总体架构主张

Agent Platform 的目标，不是为每一种智能体产品形态实现一套独立框架，而是为**动态组装、非确定、长期运行、可并行、可编程的智能执行过程**提供一套稳定的生产系统边界。

平台最终需要把这样的执行过程约束在：

> **持久、可恢复、可验证、可观测、可治理、可持续演进的系统中。**

统一心智模型：

```text
业务目标
   ↓
能力契约
   ↓
动态组装能力
   ↓
选择执行策略 / 执行框架
   ↓
统一运行时记录真实执行
   ↓
智能体工作环境执行动作、处理数据、提供反馈
   ↓
真实世界
```

同时，上下文 / 记忆、评估 / 追踪、安全与治理贯穿整个软件栈。

## 3. 每一层回答什么问题

### L7 业务 / 产品：要完成什么？

负责：

- 目标；
- 项目；
- 业务任务；
- 用户价值；
- 业务约束和责任。

对话、科研助手、知识库、编程助手、工作流产品等都属于应用形态，不等于执行范式。

### L6 能力契约：什么叫“具备这项能力”？

负责定义：

```text
能力
├── 目标 / 需求
├── 验收标准
├── 质量标准
├── 评估契约
└── 证据要求
```

执行框架描述“怎么实现”，评估描述“怎么证明”。

### L5 能力工程：智能体能学什么、能做什么？

负责组织：

- 技能（Skill）：程序性知识；
- 工具（Tool）：行动能力；
- MCP / API 绑定：连接实现；
- 能力发现；
- 能力适配器；
- 能力修订版本 / 评估。

### L4 执行策略：当前任务怎么推进？

负责：

- 直接执行；
- 工作流；
- 智能体循环；
- PTC；
- 多智能体；
- 规划；
- 委派；
- 上下文策略；
- 评估策略；
- 自主策略；
- 完成策略 / 升级策略；
- 控制权转移策略。

这些策略主要由执行框架（Harness）承载。

### L3 统一运行时：实际上发生了什么？

负责记录和管理执行生命周期、执行事实、状态视图、恢复位置、动作可靠性、取消与因果关系，并把执行框架产生的决策转化为可持久、可恢复、可治理的执行过程；不负责把某一种执行框架策略固化为系统唯一执行方式。

### L2 智能体工作环境：智能体能观察和作用于什么世界？

负责：

- 提供可持续读写的工作空间；
- 通过执行器让执行尝试真实发生；
- 把真实结果与环境变化形成高信号观察；
- 对明确世界状态进行验证并保留证据；
- 在最接近资源的位置落实隔离、权限、凭据、数据流和资源限制。

沙箱、能力代理、Worker、队列、工作空间服务等都是按部署和治理需求选择的实现机制，不是 L2 核心语义本身。

### L1 基础设施 / 真实世界：真正的资源在哪里？

包括 API、SaaS、数据库、浏览器、文件、计算资源、网络、设备等。

## 4. 核心设计原则

### 4.1 应用形态不等于执行范式

```text
应用形态
对话 · 科研 · 知识库 · 编程助手 · 行业应用

执行范式
直接执行 · 工作流 · 智能体 · PTC · 多智能体
```

同一种产品可以使用不同执行策略，同一种执行策略也可以服务多个产品。

### 4.2 工作流与智能体的真正区别是执行控制权

```text
工作流
→ 下一步主要由预定义代码 / 图决定

智能体
→ 下一步主要由模型基于上下文动态决定
```

因此：

> **静态工作流 → 动态工作流 / 计划 → 智能体循环，是一条连续谱。**

工作流图是输入表达；智能体图更接近运行时结果。

### 4.3 运行时稳定，执行框架可替换

执行框架编码了“当前模型还做不到什么”的假设。

这些假设会随着模型升级而过时，所以：

> **运行时应保持稳定；执行框架应可替换、可简化，甚至可以被移除。**

规划器、评估器、初始化器、上下文重置、待办、完成策略等默认属于执行框架，而不是运行时核心。

### 4.4 长期工作连续性不依赖智能体连续性

> **智能体可以忘记、退出或被替换；工作单元必须记住。**

长任务依赖持久工作单元状态、工作空间、事件、制品、交接和恢复，而不是一个会话永久不结束。

### 4.5 LLM 应是控制面，而不是数据面

模型适合做高价值、不确定决策；数据搬运、循环、关联、过滤、聚合和稳定机制尽量进入执行环境。

```text
智能体 / 执行框架
= 执行控制面

智能体工作环境
= 数据面 + 动作面
```

### 4.6 执行、验证、验收、发布相互分离

```text
已执行
≠ 已验证
≠ 已验收
≠ 已发布 / 已部署
```

智能体认为完成，不代表系统验证通过；验证通过，也不自动等于业务接受或允许生产发布。

### 4.7 自主性是部署特征，不是执行范式

自主性（Autonomy）描述真实部署中，智能体在多大程度上可以独立于人工直接指导和监督做出执行决策。它不是模型的固定属性，也不等于某一种执行范式。

```text
模型能力 + 执行框架
      ↓
   潜在自主性
      ↓ 受权限 / 风险 / 产品策略 / 人工监督约束
   实际自主性
```

直接执行、工作流、智能体循环、PTC、多智能体回答“任务怎么推进”；自主性回答“推进过程中，系统允许智能体自己决定多少”。

> **生产系统不应最大化自主性，而应在可验证、可观察、可干预的边界内最大化有用的自主性。**

## 5. 核心领域模型

以下中文名称对应正式代码模型 `Work / Session / Run / Event / Action / ExecutionAttempt / Observation / Artifact` 等；正文优先使用中文，Schema、事件名和代码类型保持英文。

### 5.1 工作单元（Work）

工作单元是跨智能体、会话和运行持续存在的长期领域实体，是目标、任务、资源、制品、进度、治理和验收的共同归属：

```text
工作单元
├── 目标
├── 任务 / 工作前沿
├── 能力 / 验收契约
├── 共享资源
├── 制品
├── 环境 / 工作空间
├── 长期进度
└── 会话
```

多个智能体、多个会话、多个执行框架修订版本可以围绕同一个工作单元协作。工作单元不等于项目，也不等于某个具体任务；任务是工作单元内部可独立推进、分配或验证的更小粒度对象。

### 5.2 会话（Session）

会话表示：

> **一个智能体与一个工作单元之间相对连续的认知 / 执行关系。**

会话不是聊天历史，也不是上下文窗口。会话历史只是会话范围内的一类持久信息，不能反过来定义会话本身。

同一个工作单元可以：

- 顺序经历多个会话；
- 并行存在多个会话；
- 智能体更换后继续存在。

### 5.3 运行（Run）

运行表示：

> **一次由触发器启动，并由运行时统一管理开始、挂起、恢复和终止的逻辑执行周期。**

运行不等于：

```text
HTTP 请求
Worker / 进程
一次模型调用
一次工具调用
```

一次运行可以包含多次模型调用、多个动作、多次执行尝试和子智能体委派。基础设施恢复、模型重试、动作重试、上下文压缩等内部机制通常不切断运行。

新的用户输入、定时器、Webhook 或独立外部事件可以启动新的运行；但“出现一个事件”本身并不自动意味着必须创建新运行，边界取决于原运行是否已经终止。

### 5.4 运行挂起与恢复

运行暂时没有可执行动作，不代表运行已经结束。

```text
Ready
  ↓
Running
  ↓
Suspended
  ↓ 条件满足
Ready
  ↓
Running
  ↓
Completed / Failed / Cancelled
```

常见挂起原因包括：

- 等待工具或远程任务；
- 等待子智能体；
- 等待内部定时器 / 退避；
- 等待可恢复的人工审批。

父运行以分叉 / 汇合方式等待子智能体时，可以挂起后继续同一次运行，不应因为子会话完成就机械创建新的父运行。

判断同一次运行能否继续的关键不是 CPU、Worker 或模型请求是否持续存在，而是运行时是否仍保存：

```text
这次运行在等待什么
+ 条件满足后如何继续
```

触发器只表示“有理由重新评估某个执行生命周期”，不等于一定创建新运行。用户输入、动作完成、子运行完成、人工审批、定时器或外部信号到达后，运行时需要判断是恢复现有挂起运行，还是创建新的运行。

### 5.5 事件（Event）

事件是已经发生的执行事实，是持久执行历史的重要基础。

典型类别如下。事件类型是代码标识，因此保持英文：

```text
触发器
├── UserMessageReceived
├── ExternalEventReceived
└── TimerTriggered

运行
├── RunStarted
├── RunSuspended
├── RunResumed
├── RunCompleted
├── RunFailed
├── RunCancelRequested
└── RunCancelled

动作
├── ActionRequested
├── ActionAttemptStarted
├── ActionAttemptFailed
├── ActionOutcomeUnknown
├── ActionReconciled
├── ActionSucceeded
├── ActionFailed
├── ActionCancelRequested
└── ActionCancelled

人工交互
├── ApprovalRequested
├── ApprovalGranted
├── ApprovalRejected
└── HumanInputReceived

制品
├── ArtifactCreated
└── ArtifactUpdated

恢复
├── RecoveryStarted
└── RecoveryCompleted
```

规划事件默认不属于运行时核心，因为计划属于执行框架策略。

推荐事件信封（Event Envelope）：

```text
event_id
event_type
schema_version
work_id
session_id
run_id
sequence
timestamp
actor
causation_id
correlation_id
payload
```

事件是领域事实，不是普通日志。CPU 使用率、HTTP 延迟、Token 流、标准输出分片等属于追踪、指标或日志，不应因为可观测需求而全部进入事件日志。

### 5.6 命令、事件、状态视图与执行检查点

```text
命令
→ 希望发生什么

事件
→ 实际发生了什么

状态视图
→ 根据执行事实得到的当前视图

执行检查点
→ 如果执行中断，如何继续同一次运行
```

推荐关系：

```text
领域实体当前状态 + 领域事件
          │
       原子提交
          │
          ├── 状态视图
          └── 执行检查点
```

运行、动作等领域实体拥有运行时下一步决策需要的持久当前状态；领域事件保存不可变的执行历史事实。二者应作为同一次领域状态转换的持久化原子单元提交，避免“状态成功、事件失败”或反向不一致。

状态视图服务于查询、调度、治理和展示，由当前状态与执行事实投影 / 派生，并可以重新构建。执行检查点保存执行位置、等待条件、待处理动作、子会话、审批和相关引用，用于高效恢复；它不是唯一事实源。

事件日志是**执行历史事实源**，不等于整个真实世界的事实源，也不要求运行时采用完整事件溯源。Git、数据库、SaaS 和文件系统的当前状态仍由各自系统拥有；运行时协调执行时可以直接读取持久领域实体当前状态，而不要求每次通过全量事件重放得到当前状态。

### 5.7 不同状态必须分离

“状态”不是一个可以容纳所有信息的万能对象。至少需要区分：

```text
领域实体持久状态
→ 运行、动作等当前权威执行状态

状态视图
→ 面向查询、调度和治理的当前执行事实视图

执行检查点
→ 如何恢复当前运行

执行框架状态
→ 规划、待办、评估器等策略私有状态

会话历史
→ 会话范围内的交互与历史记录

工作环境状态
→ 工作空间、浏览器、Git 和外部资源状态
```

执行框架状态由执行框架解释；运行时可以负责版本化保存和恢复，但不应把计划、待办或评估器内部结构固化成运行时领域模型。

### 5.8 动作（Action）

动作是运行时向执行世界发出的、可治理、可追踪的**逻辑执行意图**，不等于一次工具调用。

动作可以通过工具、MCP、API、Shell、代码执行、浏览器操作、人工请求或子智能体委派等方式实现。动作来源也不局限于模型，可以来自工作流、执行框架、程序、人或系统自动机制。

动作是重要的治理粒度：风险、权限、自主性、审批、可逆性和数据流策略都可以在动作级结合当前上下文进行判断。

L3 定义动作生命周期，并默认动作可能长期运行、挂起和恢复；L2 决定动作实际通过同步调用、Worker、远程任务、消息系统、轮询或回调等哪种机制执行。因此，运行时模型在语义上支持异步生命周期，但不要求所有动作在实现上都通过异步基础设施执行。

### 5.9 执行尝试（Execution Attempt）

一个逻辑动作可以经历多次真实执行尝试：

```text
动作 A1
├── 执行尝试 1 → 超时
├── 执行尝试 2 → 临时错误
└── 执行尝试 3 → 成功
```

重试产生新的执行尝试，而不是新的逻辑动作。这样运行时才能稳定回答：这是三个不同业务动作，还是同一个业务意图被执行了三次。

执行尝试承载具体执行器、开始 / 结束时间、错误、资源消耗和原始结果引用等执行细节；动作承载语义意图、治理上下文和稳定幂等身份。

### 5.10 执行尝试结果与动作判定结果

单次执行尝试返回的结果，不一定等于整个动作的最终效果。

```text
动作
 ↓
执行尝试
 ↓
执行尝试结果
 ↓
结果判定
 ↓
动作判定结果
```

例如，请求已经发送到外部系统，但响应途中连接中断：

```text
执行尝试结果 = timeout
动作判定结果 = 结果未知
```

之后通过结果核对发现外部资源实际上已经创建：

```text
动作判定结果 = Succeeded
```

因此：

> **执行尝试失败不等于动作失败；超时也不等于副作用没有发生。**

### 5.11 结果未知、幂等、重试与结果核对

动作判定至少需要区分：

```text
Succeeded
Failed
OutcomeUnknown
```

结果未知表示运行时无法确认真实副作用是否已经发生。此时不能直接把“没有收到成功响应”解释成“动作没有执行”。推荐：

```text
结果未知
   ↓
结果核对
   ↓
确认外部世界实际状态
   ↓
Succeeded / Failed
   ↓
再决定是否需要新的执行尝试
```

重试安全性不应只是运行时统一的指数退避配置，而应由能力语义和当前动作风险共同决定。常见类别包括：

- 只读 / 纯操作：通常可安全重试；
- 天然幂等操作：重复执行后最终状态一致；
- 依赖幂等键的操作：所有执行尝试必须复用同一稳定幂等身份；
- 非幂等操作：默认不能在结果未知时直接重试。

幂等键属于逻辑动作，而不属于单次执行尝试。

可靠能力除了执行入口，还可以按需要提供结果核对、取消或补偿语义。补偿本身是新的动作，通过因果关系关联原动作；不能通过修改原事件历史来假装原副作用从未发生。

### 5.12 观察（Observation）

观察是工作环境向执行框架暴露的、面向决策的世界视图。执行尝试结果、动作判定结果、资源或环境状态都可以参与构建观察：

```text
执行尝试结果
→ 这次物理执行返回了什么

动作判定结果
→ 这个逻辑动作实际上发生了什么

观察
→ 智能体应该看到什么

上下文
→ 当前模型实际加载什么
```

L2 拥有观察内容的语义，例如如何过滤、转换、聚合、脱敏和引用 Git、Browser、Shell、MCP 等原始结果；L3 负责观察与工作单元、会话、运行、动作的生命周期和来源关联；L4 的上下文策略再决定哪些观察实际进入当前模型工作集。

> **L3 决定动作实际上发生了什么；L2 决定智能体能够观察到什么；L4 决定当前模型需要看到什么。**

### 5.13 制品（Artifact）

制品是正式结果 / 交付物，具有版本、评审、发布或引用语义。

它与笔记的区别：笔记是智能体当前主观认知；制品是正式工作产物。

### 5.14 控制权转移

人工中断、纠偏、智能体主动请求澄清、风险边界触发升级等，都是实际发生的执行事实，应由运行时记录，而不是只存在于聊天文本中。

执行框架负责判断何时继续自治、何时交还控制权；运行时负责提供确定性的暂停、恢复、中断、取消和重定向能力，并记录相应事实。

```text
人委托控制权
   ↓
智能体自主执行
   ↓ 不确定性 / 信息缺失 / 能力缺口 / 风险边界
控制权转移
   ↓
人工决策 / 纠偏 / 补充信息
   ↓
继续执行或终止
```

### 5.15 L3 运行时内核

L3 的第一版实现不需要为每个领域实体建立独立 Manager。核心责任可以压缩为三个逻辑组件：

```text
统一运行时
│
├── 运行时引擎
│   ├── 触发器处理
│   ├── 运行生命周期
│   ├── 等待 / 唤醒
│   ├── 挂起 / 恢复
│   └── 恢复执行
│
├── 动作协调器
│   ├── 动作 / 执行尝试
│   ├── 结果判定
│   ├── 重试
│   ├── 结果核对
│   └── 补偿关系
│
└── 运行时存储
    ├── 领域实体持久状态
    ├── 事件日志
    └── 执行检查点
```

运行时引擎是运行生命周期的唯一推进入口；动作协调器负责把逻辑动作转成一次或多次真实执行尝试并确认最终动作判定结果；运行时存储保证领域状态转换的持久一致性。三者是逻辑组件，不要求物理上拆成三个服务。

### 5.16 执行框架与运行时控制边界

执行框架负责决定“下一步想做什么”，运行时负责把这个决定变成可持久、可治理的执行事实。最小决策集合可以保持为：

```text
Execute(actions)
Wait(condition)
Complete(output)
Fail(reason)
```

执行框架必须在产生需要治理的外部副作用、进入可能跨进程生命周期的长期等待、宣布运行完成 / 失败，或发生运行时控制权转移时把控制权交还运行时。

一次执行决策可以产生多个动作，因此同一运行保持单写者语义不意味着内部串行。多个动作和子运行可以并行，运行时负责统一协调生命周期和依赖。

执行框架不能直接修改运行、动作等运行时状态，也不能绕过动作协调器自行决定结果未知动作是否安全重试。普通模型推理通常属于执行框架内部过程；只有模型调用本身需要独立持久生命周期、恢复、调度或治理时，才需要提升为运行时动作。

### 5.17 运行时部署剖面

统一 L3 语义不意味着必须采用分布式物理部署。推荐把实现分为三个剖面：

```text
嵌入式运行时
→ 单进程协调
→ 内存 + SQLite / 本地持久化
→ 本地执行器

单节点持久化运行时
→ 单个活动运行时进程 / Pod
→ PostgreSQL 等外部持久存储
→ 本地或远程执行器
→ 进程崩溃后恢复同一次运行

分布式运行时
→ 多个运行时 Worker
→ 共享持久存储
→ 运行所有权可以跨节点迁移
→ 需要租约、版本校验、隔离机制等额外协调
```

第一版平台应优先建设**单节点、可持久恢复、支持并发动作和子运行的运行时**，而不是先建设分布式 Worker 集群。多租户规模、异构执行环境、强隔离、弹性伸缩或跨节点执行成为真实需求以后，再增量引入分布式协调。

> **逻辑组件边界不等于物理微服务边界；L3 的第一目标是持久执行，不是分布式。**

### 5.18 取消与父子运行生命周期

取消是一个控制请求，不是已经发生的事实：

```text
CancelRequested
≠
Cancelled
```

至少需要区分执行尝试取消、动作取消和运行取消。取消执行尝试只是尝试停止一次物理执行；动作取消阻止逻辑动作继续产生新的执行尝试；运行取消停止新的执行框架步骤和动作，并协调活动动作、等待条件与子运行。

取消不能回写历史。执行尝试收到取消请求后，实际结果仍可能是已取消、已完成、失败或结果未知；已经产生的业务副作用如果需要抵消，应通过新的补偿动作完成。

父子运行至少区分两类生命周期关系：

```text
结构化子运行
→ 生命周期受父运行约束
→ 父运行通常等待其完成
→ 父级取消默认可按策略向下传播

独立子运行
→ 生命周期与父运行解耦
→ 父运行无需等待
→ 父级结束或取消不自动终止它
```

运行时提供等待、取消、观察子运行状态等生命周期原语；子运行失败如何影响父运行、是否尽力聚合、是否快速失败等业务聚合策略由执行框架或委派策略决定。因此：

```text
ChildFailed ≠ ParentFailed
ParentCancelRequested ≠ EveryChildCancelled
Run terminal state ≠ World fully reconciled
```

强制终止也不等于正常取消。安全、治理或资源边界可以强制停止执行承载，但仍不能证明此前外部副作用不存在。

## 6. 上下文、记忆、工作空间

### 6.1 会话 ≠ 会话历史 ≠ 状态视图 ≠ 上下文

```text
会话
→ 智能体与工作单元的相对连续关系

会话历史
→ 会话范围内已经发生的交互与历史记录

状态视图
→ 当前执行事实视图

上下文
→ 当前模型工作集
```

上下文是查询投影，可以丢弃和重建；会话历史、状态视图和上下文都不能反过来替代会话实体。

### 6.2 上下文构建器

```text
会话历史
状态视图
记忆
笔记
制品
工作空间
技能
能力
外部资源
    ↓
上下文构建器
    ↓
  上下文
```

上下文构建器属于执行框架中的上下文策略。

### 6.3 上下文是工作集

> **上下文包含的是地图，而不是整个世界。**

稳定内容适合前置：

- 系统规则 / 策略；
- 智能体定义；
- 能力元数据。

阶段性稳定：

- 目标；
- 执行检查点的摘要 / 引用；
- 摘要；
- 当前计划。

动态内容：

- 最近历史；
- 观察；
- 即时知识；
- 工具 / 技能细节。

### 6.4 上下文压缩

```text
会话历史追加事实
      ↓
上下文策略
      ↓
选择 / 摘要 / 压缩
      ↓
上下文
```

压缩改变模型看到什么，不改变真实发生过什么。

### 6.5 笔记 / 待办

智能体当前主观工作认知，包括计划、待办、假设和临时结论。

它可以被修改，也可能是错的，因此不是事实源。

### 6.6 记忆（Memory）

可以区分：

- 工作记忆 → 笔记 / 待办；
- 情景记忆 → 过去任务 / 会话经验；
- 语义记忆 → 稳定知识、规则、偏好。

长期记忆推荐采用晋升流程：

```text
会话历史 / 观察
     ↓
候选记忆
     ↓
验证 / 来源 / 信任
     ↓
长期记忆
```

原则：

> **可以自由写入候选，但必须谨慎晋升为长期记忆。**

召回不能只用向量 Top-K，还应考虑目标、状态、范围、时效性、重要性、置信度、信任与来源。

### 6.7 工作空间（Workspace）

工作空间是工作单元范围内可被持续读取和修改的工作状态边界。它可以承载文件、代码、中间数据和生成内容，但不要求物理上一定是一个目录，也不要求第一版建设独立工作空间服务。

本地 Coding Agent 的合法第一版实现可以只是：

```text
/work/project
```

工作空间至少应可寻址，并且其工作状态不应因为一次运行或一个沙箱结束就自动消失：

```text
Workspace lifetime ≠ Run lifetime
Workspace lifetime ≠ Sandbox lifetime
```

工作空间不等于记忆，也不属于单个上下文。运行时的执行检查点可以保存工作空间引用，但不应把文件树、浏览器状态和其他外部世界状态复制进运行时状态。

快照、分支、变化集、资源版本、合并等可以由具体工作空间后端按需提供；它们是协作 / 恢复增强能力，不是工作空间核心语义的先决条件。

## 7. 能力工程

### 7.1 能力分类

```text
能力
├── 程序性能力
│   └── 技能
│
└── 行动能力
    └── 工具
```

### 7.2 工具、技能、MCP、执行框架

```text
工具
→ 能做什么动作

技能
→ 这类任务通常应该怎么做

MCP
→ 如何连接外部系统

执行框架
→ 当前任务现在怎么推进
```

### 7.3 能力适配器

```text
后端 API / MCP 工具
        ↓
能力适配器
        ↓
面向智能体的工具
```

API 原子性不等于面向智能体的能力粒度。

### 7.4 智能体决策边界

> **确定性机制下沉到能力；不确定决策留给执行框架。**

工具太原子会产生大量无意义编排；工具太大则会把真正需要智能体判断的策略藏进黑盒工作流。

### 7.5 能力目录与分类体系

```text
领域
 ↓
资源
 ↓
语义能力
 ↓
具体技能 / 工具
```

每个能力要明确“做什么”“什么时候用”“什么时候不用”以及边界和相邻能力。

### 7.6 能力发现 ≠ 能力加载

能力规模化后：

```text
能力发现
   ↓
元数据
   ↓
选择
   ↓
技能 / 工具细节加载
```

不要永久把全量工具 / 技能定义放入上下文。

### 7.7 技能渐进披露

```text
技能元数据
    ↓
SKILL.md
    ↓
参考资料 / 脚本 / 资源
```

技能是可发现、可导航、按需加载的程序性知识。

### 7.8 技能脚本与工具

技能内部脚本服务于某个技能的稳定局部实现；工具是平台级、可治理、可复用的行动能力。

不是每个脚本都需要注册成全局工具。

### 7.9 MCP 的位置

> **MCP 是连接标准，不是能力设计标准。**

推荐：

```text
技能
 ↓ 依赖
语义能力
 ↓ 绑定
工具
 ↓ 通过以下方式实现
MCP / API / 本地脚本
```

### 7.10 工具契约

```text
工具契约
├── 身份
├── 适用范围
├── 语义
├── 输入 / 输出 Schema
├── 使用指导
├── 副作用
└── 权限 / 风险
```

Schema 描述机器允许什么；使用指导帮助智能体正确选择和使用。

### 7.11 动态组装智能体

```text
基础智能体
+ 选中的技能
+ 选中的工具
+ 召回的知识
+ 任务上下文
       ↓
实际工作的智能体
```

> **智能体使用能力，但不拥有能力。**

能力资产应独立、可版本化、可发现、可组合、可治理。

### 7.12 评估驱动的能力工程

工具和技能都从真实能力缺口出发，通过试验、追踪、评估持续迭代。

工具使用异味包括：错误工具切换、重复重试、结果过大、参数无效等。

技能失败包括：发现失败、错误激活、导航失败、指令失败、上下文过载、过程失败。

## 8. 执行策略

### 8.1 直接执行

模型直接做一次决策或直接调用少量工具。

### 8.2 工作流

代码拥有主要执行控制权。

基础控制原语：

- 顺序；
- 分支；
- 分叉 / 汇合；
- 循环；
- 动态展开。

### 8.3 智能体循环

模型持续根据上下文和观察决定下一动作。

### 8.4 PTC

PTC（Programmatic Tool Calling，程序化工具调用）是工具编排模式，不是工具类型。

```text
模型
 ↓ 生成程序
程序
 ├── 工具 A
 ├── 工具 B
 ├── 循环
 ├── 过滤
 └── 聚合
      ↓
观察
 ↓
模型
```

一个推理步骤可以对应许多环境动作。

### 8.5 多智能体

使用多智能体取决于：

```text
价值
≈ 可并行性
 + 上下文独立性
 + 结果可合并性
 - 依赖密度
 - 协调成本
```

复杂任务本身不是理由。

### 8.6 自主策略与执行策略正交

工作流、多智能体或智能体循环本身不能说明系统的自主程度。同一执行范式可以在不同权限、风险和人工监督配置下表现出完全不同的实际自主性。

自主策略应由执行框架结合任务风险、可逆性、验证能力、权限范围和人工监督能力动态决定，而不是作为产品或模型的固定等级。

## 9. 多智能体架构

### 9.1 主智能体（Lead Agent）

> **主智能体 = 编排者 + 全局上下文负责人。**

负责全局目标、工作拆解、委托、覆盖度、冲突和最终综合。

### 9.2 智能体即工具 vs 子会话

智能体即工具：聚焦短调用，是父会话中的一次动作。

自治子智能体：拥有独立目标、多轮上下文、制品和恢复能力，需要独立子会话。

### 9.3 动态团队形成

```text
目标
+ 能力
+ 知识
+ 权限
+ 预算
+ 风险
   ↓
执行框架
   ↓
单智能体 / 工作流 / 多智能体 / 混合模式
```

智能体团队本身可以是运行时结果。

### 9.4 工作前沿

工作前沿是当前独立、可领取、可验证的工作项集合。

> **有效并行度约等于独立工作前沿的数量。**

多智能体的关键是工作调度器，而不是智能体调度器。

### 9.5 共享状态 + 局部隔离

单个 Agent / 单体运行时并不要求资源身份、租约或冲突系统。只有多个 Agent 需要并发作用于同一个共享世界时，协作环境才需要逐步增强：

- 共享资源；
- 隔离的局部工作空间；
- 资源身份 / 版本；
- 所有权 / 租约；
- 快照 / 变化；
- 冲突处理。

这些是协作 / 分布式工作环境的机制增强，而不是 L2 Core 的先决条件。协作可以通过环境状态发生，也不必全部依赖智能体之间直接传消息。

### 9.6 局部恢复 + 全局协调

子任务局部失败优先局部恢复；结果回到父级重新协调全局计划。

### 9.7 两层并发

- 委派并发；
- 动作 / 工具并发。

两层拥有独立预算和背压策略。

### 9.8 信任感知的智能体交接

智能体之间的结果不应该只是一段文本：

```text
智能体消息 / 委派结果
├── semantic_type
├── content
├── provenance
├── evidence_refs
├── confidence
└── trust_label
```

信息经过转换不会自动提升信任等级。

## 10. 智能体工作环境

L2 的目标不是构造一个庞大的 Workspace / Sandbox 平台，而是提供一个**可持续修改、可执行、可观察、可验证，并能够真正落实安全与治理边界的工作世界**。

### 10.1 四个核心语义

```text
智能体工作环境
│
├── 工作空间
│   └── 工作状态连续性
│
├── 执行器
│   └── 真实动作执行
│
├── 观察
│   └── 面向智能体的世界投影
│
└── 验证
    └── 面向系统的世界状态判定
```

沙箱、能力代理、凭据解析、数据流策略、资源限制、Worker、队列和工作空间服务等属于横切机制或部署增强，不应替代这四个稳定语义。

### 10.2 工作空间：保存世界连续性

工作空间保存工作单元推进过程中需要持续存在的可修改状态。它和执行器 / 沙箱分离，也和运行生命周期分离：

```text
Workspace lifetime ≠ Run lifetime
Workspace lifetime ≠ Sandbox lifetime
```

本地 Agent 完全可以直接用一个目录作为工作空间。上云以后可以替换成持久卷或其他持久存储，而不改变 L2 语义。

运行时执行检查点只保存必要的工作空间引用；工作空间内容仍属于 L2 世界状态。

### 10.3 执行器：让执行尝试真实发生

执行器接受一次执行尝试，在指定工作环境里执行，并返回执行尝试结果：

```text
L3 动作协调器
      ↓
   执行尝试
      ↓
L2 执行器
      ↓
工作空间 / 真实世界
      ↓
执行尝试结果
```

工具 / 能力定义“能做什么”，执行器定义“这次具体怎样执行”。同一个能力可以绑定本地 Shell、远程任务、浏览器、HTTP、MCP 等不同执行实现。

短执行可以直接返回结果；长执行可以返回不透明的外部执行引用，并在之后通过查询、回调或信号确认完成。是否采用 Worker、队列、远程任务系统属于实现选择。

执行器调用失败也不等于真实副作用一定没有发生；结果未知仍由 L3 的动作结果判定与结果核对语义处理。

### 10.4 观察：面向智能体的世界投影

观察不是工具结果的简单包装，而是工作环境根据执行结果、当前世界状态和外部变化形成的面向决策投影：

```text
执行结果 / 当前环境 / 外部变化
            ↓
选择 · 过滤 · 结构化 · 聚合 · 脱敏 · 引用
            ↓
           观察
```

观察目标是提高决策信号，而不是最大化原始信息量。大日志、DOM、API 响应等可以保留为原始证据引用，只把当前决策需要的摘要和结构化信息放进观察。

观察还必须保留来源与信任信息；信息经过摘要、转换或另一个 Agent 转述，不会自动提升信任等级。

观察不等于上下文。L2 形成世界投影，L4 上下文策略决定当前模型实际加载哪些观察。

### 10.5 验证：面向系统的世界状态判定

验证针对明确目标状态应用条件并产生结果 / 证据：

```text
目标状态
+
验证条件
+
验证方法
      ↓
验证结果
+
证据
```

文件存在、测试通过、Schema 有效、数据库资源存在、服务健康等都属于验证问题。

> **Agent 主观判断不等于验证事实。**

验证器可以复用执行器，例如通过 Shell 跑测试；但“执行命令”和“判断目标状态是否成立”仍然是不同语义。

验证结果必须能关联到实际被验证的状态。工作空间再次修改后，旧的测试通过结果不能自动证明新状态仍然有效；可以直接复用 Git tree hash、内容哈希、资源版本等已有机制，而不要求统一建设工作空间版本系统。

### 10.6 验证、评估、验收分层

```text
验证
→ 当前世界状态是否满足明确条件

评估
→ 结果质量是否达到能力要求

验收
→ 业务是否接受这个结果
```

真正边界不是“规则还是 LLM”：视觉检查可以使用模型完成验证，但如果它判断的是一个明确世界状态条件，语义仍然属于验证。

完成决策应尽量建立在验证证据上，而不是仅仅建立在动作调用成功上。

### 10.7 沙箱与约束执行

工作环境不等于沙箱。沙箱只是某些执行器使用的隔离承载，用来限制文件、网络、凭据、进程、计算资源和其他能力的可达范围。

安全 / 治理负责决定边界；L2 在最接近真实资源的位置强制执行这些边界：

```text
L5 能力
→ 描述能力需要什么权限 / 资源

安全 / 治理
→ 决定本次允许范围

L3 运行时
→ 把决策绑定到动作 / 执行尝试并记录生命周期

L2 工作环境
→ 真正执行文件、网络、凭据、数据和资源限制
```

> **只有策略判断，没有可强制执行的边界，就不构成安全保证。**

能力代理是受治理动作出口的一种实现，但不要求物理上成为独立服务；单体程序里的文件执行器或 HTTP 执行器本身就可以承担约束执行职责。

### 10.8 执行权限 ≠ 模型可见性

系统可以被允许处理某些数据，而模型不一定应该直接看到这些数据：

```text
执行权限
≠ 模型可见性
```

例如执行器可以把文件流式上传到批准的对象存储，而模型只看到资源引用和执行状态。

因此数据策略至少在两个方向执行：

```text
动作出口
→ 控制能把什么数据发送到哪里

观察入口
→ 控制什么数据可以进入模型可见观察
```

具体凭据解析和使用发生在 L2 执行边界，不应把长期密钥直接暴露给执行框架。

### 10.9 三个部署剖面

统一 L2 语义不意味着必须从分布式环境起步。

```text
本地嵌入式环境
→ 本地目录 + subprocess / 文件 API / HTTP client
→ 单写者，无租约、无工作空间服务

单节点持久化环境
→ 持久工作空间 + 本地 / 远程执行器
→ 沙箱退出后工作空间继续存在

分布式 / 协作环境
→ 多 Worker / Agent 跨节点访问或并发修改共享世界
→ 按需增加定位、资源版本、租约、冲突、路由、去重、容量和背压
```

> **先解决工作状态连续性，再解决多主体协作。**

租约、工作发现、资源级冲突和远程 Workspace Service 等不属于 L2 Core 的先决条件。

### 10.10 第一版可以非常小

```text
Python / Go Process
│
├── L3 Runtime
├── L4 Harness
└── L2 Work Environment
    ├── Workspace: /work/project
    ├── File / Shell Executor
    ├── Observation Adapter
    └── Verifier
```

单体实现已经可以完整满足 L2 语义。后续上云或分布式，只增加持久化、隔离、路由与协调机制，不改变核心执行链。

## 11. 数据面

### 11.1 数据可见性

```text
模型可见数据
仅执行环境可见数据
持久资源
```

智能体系统可以被允许处理某些数据，而模型不被允许直接看到这些数据。

> **执行权限不等于模型可见性。**

L2 的动作出口负责约束数据可以被发送到哪里；观察入口负责约束哪些数据可以进入模型可见观察。允许执行器处理一份数据，不代表必须把原始数据复制进上下文。

### 11.2 数据流策略

```text
来源
+ 数据分类
+ 目的地
+ 能力
+ 主体 / 租户
+ 用途 / 工作单元上下文
      ↓
允许 / 拒绝 / 脱敏
```

能力权限与数据流权限不是同一个维度。

## 12. 评估架构

### 12.1 试验（Trial）是基本单位

```text
评估套件
   └── 任务
        └── 试验
             ├── 执行框架修订版本
             ├── 能力修订版本
             ├── 环境修订版本
             ├── 过程记录 / 追踪
             ├── 最终结果
             └── 评分结果
```

### 12.2 过程记录 / 追踪与最终结果

追踪描述过程发生了什么；最终结果描述执行后真实世界和结果是什么。

二者必须分离。

### 12.3 评估契约

```text
评估契约
├── 评估标准
├── 证据来源
├── 评分器
├── 阈值 / 关键程度
└── 聚合方式
```

### 12.4 评分器

- 确定性评分器；
- LLM 评分器；
- 人工评分。

评估标准、证据和评分器分开建模。

### 12.5 非确定性

- pass@k：至少一次成功，更接近能力上限 / 搜索潜力；
- pass^k：全部成功，更接近可靠性。

### 12.6 能力评估与回归评估

能力评估探索能力边界；成功案例逐渐晋升到回归套件，守住已有能力。

### 12.7 评估基础设施与评估内容

平台负责运行器、环境、追踪、评分器 SDK、统计、版本管理。

领域 / 能力负责人负责任务、标准、评分规则、参考解法、失败案例、领域评分器。

> **评估基础设施是平台能力；评估内容是能力资产。**

### 12.8 评估是能力规格

```text
执行框架
→ 如何实现

评估
→ 如何证明
```

### 12.9 上线前评估与部署评估

上线前评估回答“在受控条件下能不能做到”；部署后监控与部署评估回答“在真实用户、真实权限和真实任务下实际上如何运行”。

```text
能力定义
   ↓
上线前评估
   ↓
发布 / 部署
   ↓
部署后监控
   ↓
真实行为 / 失败模式
   ↓
形成新的评估任务
   ↓
回归评估
   ↓
执行框架 / 能力修订
```

生产失败不应止于修复单个问题，而应尽量沉淀为可重复的评估任务和回归用例。

## 13. 验证架构

验证关注明确世界状态是否满足条件；评估关注能力质量；验收关注业务是否接受。三者可以共享证据，但不应混成同一状态。

### 13.1 验证阶梯

```text
本地检查
   ↓
回归验证
   ↓
代表性工作负载
   ↓
集成验证
   ↓
类生产环境验证
```

验证结果需要关联到实际被验证的目标状态。资源或工作空间发生变化后，应重新确认相关验证证据是否仍然有效。

### 13.2 差异判定器

验证器应尽量告诉智能体“差在哪里、下一步如何定位”，而不仅是通过 / 失败。

### 13.3 质量守护者

维护跨工作项的长期质量维度，例如回归、架构约束、技术债和共享资源健康。

### 13.4 单次成功结果成本

最终成本指标关注“一个成功结果需要多少总资源”，而不是单次 token / request 价格。

## 14. 安全与治理

安全目标可以理解为：

```text
部署风险
≈ 失败概率 × 影响半径
```

模型 / 分类器 / HITL 主要降低失败概率；隔离控制负责限制最大影响半径。

### 14.1 三类风险来源

```text
用户误用
模型错误行为
外部攻击 / 提示词注入
```

因此需要纵深防御：

```text
行为安全
内容安全
环境安全
```

### 14.2 上下文入口边界

外部内容进入上下文前经过：

```text
原始内容
   ↓
来源信息
信任分类
提示词注入检测
数据检查
脱敏 / 清洗
策略
   ↓
观察
   ↓
上下文
```

可信工具不等于可信工具输出。

### 14.3 信任生命周期

```text
已发现
  ↓
不可信
  ↓
可信读取
  ↓
可信指令
  ↓
可信执行
```

本地性不等于可信。

对于智能体，“读”本身可能影响行为，因此信任边界需要覆盖解析、加载和解释。

### 14.4 信任传播

信任跟随数据来源传播，而不是因为信息经过内部智能体就自动升级。

```text
信息转换
≠ 信任提升
```

### 14.5 智能体身份

推荐身份链：

```text
人类主体
   ↓ 委派
智能体主体
   ↓ 收窄权限
执行主体
   ↓ 使用
范围受限的凭据
```

区分：

```text
身份 → 我是谁
委派 → 我代表谁
权限 → 我能做什么
凭据 → 我如何证明权限
```

### 14.6 授权模型

核心授权单元：

```text
主体
× 委派链
× 能力
× 资源
× 范围
× 时长
× 工作单元上下文
```

委派传递目标，不默认复制权限。

### 14.7 即时能力授权

权限按工作单元 / 阶段动态收缩：

```text
任务需要
  ↓
能力请求
  ↓
策略
  ↓
临时范围授权
  ↓
执行
  ↓
撤销 / 收窄
```

最小权限进一步扩展为：

```text
最小权限
× 最短时长
× 最小范围
```

### 14.8 隔离控制 = 可达范围控制

隔离控制不只是 `sandbox=true`，而是控制当前智能体可触达的世界：

```text
智能体可达范围
├── 文件系统
├── 网络
├── 凭据
├── 能力
├── 数据
├── 记忆
├── 其他智能体
└── 外部系统
```

目标是让每个工作单元 / 运行 / 子智能体的可达图尽可能小。

### 14.9 隔离配置

```text
隔离配置
├── isolation_mode
├── filesystem_scope
├── network_scope
├── credential_scope
├── resource_budget
├── allowed_capabilities
├── approval_boundary
└── user_oversight_level
```

隔离强度需要匹配风险、自主程度和用户监督能力。

### 14.10 出站治理

域名白名单不够：一个域名可能承载大量不同能力和租户。

```text
出站治理
├── 目的地
├── 协议
├── 能力
├── 凭据
├── 租户 / 主体
├── 数据分类
└── 来源信息
```

> **允许访问某个域，本质上是一组能力授权，而不是简单的目的地过滤。**

### 14.11 记忆治理

长期记忆写入近似于修改未来智能体的启动上下文，因此需要：

- 来源信息；
- 信任；
- 晋升；
- 验证；
- 启动扫描；
- 信任感知召回。

不可信内容被智能体总结后，不能自动变成高可信记忆。

### 14.12 用户意图与能力边界

来自用户的指令也可能由攻击者诱导产生。

```text
指令来源
≠ 意图来源
```

用户意图定义目标，但系统能力边界独立存在。

HITL 不应该承担用户根本无法理解的底层安全决策。

### 14.13 隔离与可观测性

强隔离可能降低宿主机可见性，因此需要带外遥测通道。

```text
治理
= 策略
+ 执行约束
+ 可观测性
```

### 14.14 经验证的基础原语

智能体特有创新优先放在治理 / 策略组合；隔离 / 约束执行尽量复用成熟基础设施：

- Hypervisor；
- OS 沙箱；
- seccomp / namespace；
- 文件系统 ACL；
- firewall / proxy；
- IAM / 范围受限凭据；
- 资源限制。

> **治理决定边界画在哪里；成熟基础设施保证智能体越不过这条边界。**

> **只有策略判断，没有在最接近资源处的约束执行，就不构成安全保证。**

### 14.15 自主性与风险联合治理

自主性与风险是两个正交维度。高自主并不自动意味着高风险，低自主动作也可能因为资源范围或后果不可逆而具有高风险。

```text
自主空间
受以下因素共同约束：
风险 × 可逆性 × 可达范围 × 验证能力 × 人工监督能力
```

更成熟的策略是在动作级动态决定控制权：低风险、可逆、可验证区域可以自动执行；高风险边界触发人工监督、升级或确定性拒绝。

> **隔离控制决定最多能触达到哪里；自主策略决定在这个边界内可以自己决定多少。**

## 15. 可观测性与追踪

### 15.1 智能体追踪

用于理解智能体为什么这么做：

- 模型步骤；
- 工具选择；
- 委派；
- 评估；
- 最终结果。

### 15.2 运行时追踪

围绕工作单元、会话、运行、事件、动作和执行尝试记录完整执行关系。动作与执行尝试分离以后，既可以观察逻辑业务意图，也可以分析具体重试、超时、执行器和成本。

### 15.3 安全追踪

来自更接近约束执行的位置：

- 进程启动；
- 文件系统访问；
- 网络出站；
- 凭据使用；
- 策略决策；
- 沙箱违规。

智能体追踪与安全追踪可以通过 `work_id`、`session_id`、`run_id`、`action_id`、`correlation_id` 关联，但不应完全依赖同一个采集机制。

### 15.4 PTC 追踪

层级关系：

```text
推理步骤
  ↓
程序
  ├── 动作 A
  ├── 动作 B
  ├── 动作 C
  └── 策略决策
```

不能只记录 `CodeExecutionSucceeded`。

### 15.5 自主性遥测

自主性不是运行时事实字段，而是基于运行、动作和控制权转移事实形成的测量投影：

```text
运行 / 动作 / 控制权转移事件
              ↓
          自主性投影
              ↓
连续自主时长 · 人工干预 · 主动升级 · 自主完成率 · 风险分布
```

自主性指标必须与最终结果、验证通过率和风险联合解释，不能单独优化“运行更久”或“减少人工介入”。

### 15.6 部署后监控

真正理解智能体行为需要工作单元、会话、运行级的执行关联，而不能只记录单次模型请求或工具调用。

部署后监控应在隐私保护前提下记录足够的结构化事实，例如控制权转移、策略决策、动作元数据、动作判定结果和验证状态，并将真实失败模式反哺回归评估。

## 16. 恢复与升级

### 恢复

解决当前能力范围内的暂时故障：

- worker restart；
- 执行框架崩溃；
- 临时能力故障；
- 可安全重试的执行尝试失败；
- 通过执行检查点恢复挂起运行；
- 对结果未知动作进行结果核对。

恢复的第一原则不是“没有成功事件就重试”，而是先区分明确失败与结果未知。对于可能已经产生外部副作用的动作，恢复必须先确认真实世界状态，再决定是否创建新的执行尝试。

恢复不是回到原进程中的某一行代码，而是把同一次运行恢复为可继续决策和执行的语义状态。因此：

```text
Process lifetime ≠ Run lifetime
Worker failure ≠ Run failure
```

内存状态只是执行缓存；凡是进程直接终止后丢失会改变业务执行语义的信息，都必须进入可恢复的持久状态、事件、执行检查点或引用。

### 升级

解决能力边界：

- 更强模型；
- 专项能力；
- 人工决策；
- 新工具；
- 缩小范围。

> **恢复解决暂时失败；升级解决能力上限。**

升级也承担控制权交还职责：当不确定性、信息缺失、权限或风险超过当前自主边界时，执行框架应主动升级，而不是持续猜测或无界重试。

## 17. 执行框架工程

执行框架是持续实验对象：

```text
执行框架修订版本
      ↓
     试验
      ↓
追踪 + 最终结果
      ↓
     评估
      ↓
   失败分析
      ↓
执行框架修订版本
```

执行框架修订版本、技能修订版本、工具修订版本、评分器修订版本都应该被版本化。

执行框架发布不等于正在执行的会话自动迁移。

## 18. 能力生命周期

系统中的可复用能力应该经过明确生命周期：

```text
能力缺口
   ↓
候选
   ↓
原型
   ↓
能力评估
   ↓
安全 / 治理评审
   ↓
发布修订版本
   ↓
回归评估
   ↓
生产反馈
   ↓
修订 / 废弃
```

对于生成代码：

```text
临时代码
→ 工作空间代码
→ 候选能力
→ 评估 / 评审
→ 技能 / 工具 / 其他可复用能力
```

智能体可以提出候选能力，但不能在活跃生产会话中无治理地自行发布。

## 19. 人类治理与监督

### 19.1 人类治理面

随着智能体自主性增强，人类角色从：

```text
逐步指导执行路径
```

转向：

```text
治理面
├── 目标
├── 能力 / 验收
├── 风险边界
├── 预算
├── 升级
├── 生产验收
└── 发布 / 部署决策
```

HITL 仍然重要，但它应主要承担人类有能力做出的语义决策，而不是替代沙箱、凭据隔离、出站策略等系统硬边界。

### 19.2 人工监督面

人工监督面关注运行过程中，人如何保持态势感知并在需要时改变执行轨迹：

```text
人工监督面
├── 进度投影
├── 风险可见性
├── 动作 / 计划可见性
├── 暂停 / 恢复
├── 中断
├── 纠偏 / 实时引导
├── 审批
├── 评审
├── 验收
└── 升级
```

人工监督面与人类治理面语义不同：治理面决定目标、边界、预算和最终验收；监督面负责执行过程中如何观察、介入和纠偏。

有效监督的判断标准不是“是否对每个动作审批”，而是人是否真正处于能够看清状态、理解风险并及时介入的位置。

## 20. 核心架构不变量

1. **应用形态不等于执行范式。**
2. **工作流与智能体的核心区别是执行控制权归属。**
3. **运行时管理执行事实，执行框架管理执行策略，业务层管理工作意图。**
4. **运行时应稳定，执行框架应可替换、可简化甚至消失。**
5. **工作单元是长期连续性的载体；智能体、会话、上下文都可以被替换或重建。**
6. **工作单元、会话、运行分别表示长期工作实体、智能体与工作单元的连续关系、一次受运行时管理的逻辑执行周期。**
7. **运行可以挂起并恢复；进程、Worker、模型请求或子智能体完成都不能机械定义运行边界。**
8. **事件是执行事实，状态视图是由事实投影 / 派生的当前视图，执行检查点是恢复载体。**
9. **事件日志是执行事实源，不是整个外部世界的事实源；平台不要求所有对象采用完整事件溯源。**
10. **状态视图、执行检查点、执行框架状态、会话历史和工作环境状态必须分离。**
11. **上下文是工作集和查询投影，不是事实源。**
12. **上下文压缩改变模型看到什么，不改变真实历史。**
13. **笔记是主观工作认知，记忆是跨时间保留信息，工作空间是可持续修改的外部工作状态边界，制品是正式产物。**
14. **动作是逻辑执行意图，不等于工具调用；执行尝试是一次真实执行。**
15. **执行尝试失败不等于动作失败；超时不等于副作用没有发生。**
16. **结果未知必须先核对真实外部状态，再决定是否重试。**
17. **同一动作的多次执行尝试共享稳定幂等身份；补偿通过新的动作表达，不重写历史。**
18. **L3 定义动作生命周期和可靠性语义，L2 负责具体执行、世界观察、验证和约束执行。**
19. **执行尝试结果、动作判定结果、观察和上下文属于不同层次；观察是面向智能体的世界投影。**
20. **工具是行动能力，技能是程序性知识，MCP 是连接标准，执行框架是当前执行策略。**
21. **智能体可以由基础智能体 + 技能 + 工具 + 知识 + 任务上下文动态组装。**
22. **能力发现与能力加载必须分离。**
23. **确定性机制下沉到能力，不确定决策留给执行框架。**
24. **LLM 应是控制面，而不是数据面。**
25. **PTC 是执行策略，不是工具类型；一个推理步骤可以展开多个受治理动作。**
26. **代码执行权限不等于业务能力权限；执行权限也不等于模型可见性。**
27. **多智能体的关键不是智能体数量，而是工作前沿和共享工作环境；资源版本、租约与冲突属于协作环境增强，而非单体先决条件。**
28. **主智能体负责全局编排和全局上下文；子会话负责局部自治工作。**
29. **委派传递目标，不默认复制权限。**
30. **试验是智能体评估的基本单位；过程记录 / 追踪与最终结果分离。**
31. **最终结果是事实，评估分数是测量投影。**
32. **评估是可执行的能力规格：执行框架说明怎么实现，评估说明怎么证明。**
33. **能力评估探索能力边界，回归评估守住已获得能力。**
34. **执行、验证、验收和发布 / 部署状态必须分离。**
35. **智能体安全同时治理上下文入口、信任传播、执行边界和出站。**
36. **可信能力不代表可信观察。**
37. **信任跟随来源信息传播，不因经过内部智能体或智能体摘要自动升级。**
38. **用户意图可以定义目标，但不能自动扩大能力边界。**
39. **智能体应成为可独立授权、审计和撤销的主体，同时保留人类委派链。**
40. **隔离控制的本质是可达范围控制：让智能体可达世界保持任务所需最小范围。**
41. **最小权限还要结合最短时长与最小范围。**
42. **概率型防御降低失败概率，确定性隔离限制最大后果。**
43. **治理定义边界；最接近资源的成熟基础设施和 L2 执行点真正落实边界。**
44. **治理 = 策略 + 约束执行 + 可观测性。**
45. **人类应逐渐从执行路径移向目标、风险、验收和升级所在的治理面。**
46. **自主性不是模型或执行范式的固定属性，而是模型、执行框架、权限、产品设计和人工监督共同形成的部署特征。**
47. **执行策略回答任务怎么推进；自主策略回答在既定边界内智能体可以自己决定多少。**
48. **控制权转移是执行事实，自主性指标是基于这些事实形成的测量投影。**
49. **自主性必须与风险、可逆性、可达范围和验证能力联合治理，而不能被单独最大化。**
50. **有效人工监督不等于逐步审批，而是能够持续观察，并在需要时中断、纠偏、升级或验收。**
51. **上线前评估测能力潜力，部署后监控测真实行为；生产反馈应持续反哺回归评估。**
52. **领域实体当前状态与领域事件应形成同一次持久状态转换；运行时不要求完整事件溯源。**
53. **运行时引擎管理运行生命周期，动作协调器管理动作可靠性，运行时存储管理持久一致性。**
54. **执行框架负责决策，运行时负责持久执行语义，工作环境负责真实执行与观察。**
55. **执行尝试结果、动作判定结果、观察和上下文属于不同层次，不能互相替代。**
56. **进程生命周期不等于运行生命周期；进程或 Worker 失败不等于运行失败。**
57. **L3 的第一目标是持久执行，不是分布式；分布式协调属于部署剖面的增量机制。**
58. **逻辑组件边界不等于物理微服务边界。**
59. **取消请求不等于取消完成；取消不会重写已经发生的事实。**
60. **子运行失败不等于父运行失败；父运行取消也不等于所有子运行都已成功取消。**
61. **运行进入终态不等于外部世界已经完全核对和收敛。**
62. **工作环境不等于沙箱；沙箱只是限制执行可达范围的隔离机制之一。**
63. **工作空间生命周期不等于运行或沙箱生命周期；L3 保存引用，不复制整个工作世界。**
64. **能力 / 工具定义能做什么，执行器定义一次执行尝试具体怎样发生。**
65. **执行器调用失败不等于外部执行一定失败；真实副作用仍由动作结果判定语义收敛。**
66. **观察是环境状态的高信号投影，不是工具结果包装，也不等于上下文。**
67. **Agent 主观判断不等于验证事实；验证必须面向明确目标状态并保留可追溯证据。**
68. **验证、评估、验收分别回答世界状态、能力质量和业务接受三个不同问题。**
69. **只有策略判断，没有最接近资源处的约束执行，就不构成安全保证。**
70. **L2 先解决工作状态连续性，再按真实需求增加多主体协作和分布式协调机制。**

## 21. 一句话总结

> **Agent Platform 的核心，不是“跑一个智能体循环”，而是把一个动态组装、非确定、长期、并行、可编程的智能执行过程，约束在持久、可恢复、可验证、可观测、可治理、能够持续演进的生产系统中。**
