# 智能体平台总体架构

本文档记录 Agent Platform 当前已经形成的规范性架构结论，并随着研究持续演进。

> 当前版本主要吸收《Building effective agents》带来的架构结论。

## 1. 架构主张

Agent Platform 不应该按“对话 Agent、科研 Agent、知识库 Agent、工作流 Agent”等产品形态分别建设执行内核。

更稳定的抽象是：

```text
业务 / 产品
    ↓
执行策略
    ↓
统一运行时
    ↓
外部能力与真实世界
```

应用形态决定用户需要完成什么，执行策略决定任务如何推进，统一运行时负责承载真实发生的执行过程。

## 2. 核心设计原则

### 2.1 应用形态与执行范式分离

对话、研究、知识库、Coding 等是应用形态；直接执行、工作流和智能体是执行范式。两者不建立一一对应关系。

### 2.2 执行控制权是工作流与智能体的核心边界

- 工作流：下一步主要由预定义代码或图决定。
- 智能体：下一步主要由模型根据当前上下文动态决定。

因此，运行时不绑定某一种控制方式。

### 2.3 执行方式是一条连续谱

```text
Direct
  ↓
静态 Workflow
  ↓
动态 Workflow / Plan
  ↓
Agent Loop
```

复杂度和自主性应按任务需要逐渐增加，而不是默认使用完全自治智能体。

## 3. 初始软件栈

```text
L4 业务 / 产品
   Goal · Application

L3 执行策略
   Direct · Workflow · Agent Loop

L2 统一运行时
   Execution · State · Action · Result

L1 外部能力 / 真实世界
   Model · Tool · API · DB · Browser · Files
```

这一分层仍是初始版本，后续研究会继续拆分运行时、能力层和执行环境。

## 4. 执行策略

### 4.1 工作流控制原语

文章中的典型模式可以归约为：

- 顺序执行（Sequence）
- 条件分支（Branch）
- 分叉 / 汇合（Fork / Join）
- 循环（Loop）
- 动态展开（Dynamic Expansion）

工作流 DSL 和 DAG 属于上层表达，可以被映射到这些执行控制能力。

### 4.2 工作流图与智能体执行图

```text
Workflow Graph
= 执行前给定的输入结构

Agent Graph
= 运行过程中动态形成的执行结果
```

因此统一运行时不应以固定 DAG 作为唯一事实模型。

### 4.3 多智能体的位置

当前阶段将多智能体视为更高层的执行拓扑，而不是统一运行时的基础原语。是否需要多个 Agent 应由执行策略根据任务特征决定。

## 5. 当前架构不变量

1. **应用形态不等于执行范式。**
2. **工作流与智能体的核心区别是执行控制权归属。**
3. **统一运行时负责承载执行事实，不固化某一种“下一步如何决定”的策略。**
4. **静态工作流、动态计划和 Agent Loop 是执行控制逐渐动态化的连续谱。**
5. **Workflow Graph 是输入表达；Agent Graph 更接近运行时结果。**
