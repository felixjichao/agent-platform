# L3 统一运行时

> **运行时（Runtime）的核心职责不是替智能体决定怎么做，而是把真实执行变成有身份、有生命周期、可持久、可恢复、可追踪、可治理的系统事实。**

## 1. L3 管什么，不管什么

三个关键执行层的边界是：

```text
L4 执行策略 / 执行框架
→ 决定当前任务怎么推进

L3 统一运行时
→ 管理执行生命周期、事实、恢复与可靠性

L2 智能体工作环境
→ 真正执行动作并作用于外部世界
```

规划、待办、评估器、上下文策略等属于执行框架；Worker、队列、远程任务、沙箱、MCP 传输等具体执行机制属于工作环境。L3 只保留跨执行策略和执行机制都稳定的运行时语义。

## 2. 三个时间尺度：工作单元、会话、运行

```text
工作单元（Work）
   ↓
会话（Session）
   ↓
运行（Run）
```

**工作单元**承载长期工作连续性。目标、任务、共享资源、制品、工作空间、进度、治理与验收都围绕工作单元持续存在；智能体、模型和执行框架都可以被替换。

**会话**表示一个智能体与一个工作单元之间相对连续的认知 / 执行关系。它不是聊天线程，也不是上下文窗口；会话历史只是会话拥有的一类信息。

**运行**表示一次由触发器启动，并由运行时统一管理开始、挂起、恢复和终止的逻辑执行周期。它不等于 HTTP 请求、Worker、模型请求或工具调用。

## 3. 挂起不等于运行结束

运行可以暂时没有可执行动作，但仍然保持同一个逻辑生命周期：

```text
Ready
  ↓
Running
  ↓
Suspended
  ↓ 条件满足
Ready
  ↓
Running
  ↓
Completed / Failed / Cancelled
```

常见挂起包括等待工具、远程任务、子智能体、内部定时器或可恢复审批。

例如父智能体分叉多个子智能体并等待结果：

```text
父运行
  ↓
创建子会话 / 子运行
  ↓
父运行挂起
  ↓
子智能体完成
  ↓
父运行恢复
```

这仍然可以是同一次父运行。判断是否连续的关键不是进程是否一直存活，而是运行时是否仍然保存“正在等待什么，以及条件满足后如何继续”。

触发器只表示“有理由重新评估某个执行生命周期”，不等于一定创建新运行。用户输入、动作完成、子运行完成、人工审批、定时器或外部信号到达后，运行时需要判断是恢复现有挂起运行，还是创建新的运行。

### 3.1 入口接收、路由与运行输入

运行级信号不是外部输入的接收前提。入口事件 / 触发器可以先绑定工作单元或会话，不要求已有 `run_id`；接收时先按来源及稳定事件身份去重并持久保存载荷引用。它们是接收与路由协议记录，不新增核心领域实体。

L3 按确定性路由规则处理未路由记录：有明确关联的活动运行则向该运行投递并重新评估唤醒条件；会话没有活动运行且该输入允许启动工作时，执行 `CreateRun(initial_input_ref)`；多个候选且无法确定，或缺少启动授权时，保留待路由状态及明确原因，等待补齐条件。已终止运行的迟到动作结果进入核对流程，不因收到结果自动新建运行。

路由提交在同一事务内记录路由结果、必要的新运行及创建事件、初始输入 / 运行级信号投递、决策上下文修订号和待唤醒状态，并将入口记录标为已路由。以入口身份约束路由结果唯一，新运行不能先于输入绑定对调度可见。崩溃发生在路由提交前则重试未路由记录，发生在提交后则复用既有运行及投递，不能重复创建运行或丢输入。并发接收针对同一会话的输入时，路由在会话作用域串行判定已有运行，避免都看到“没有活动运行”。

入口已持久接收与输入已对运行生效是两个确认点。已知运行的纠偏 / 取消应在接收事务内完成路由或控制请求提交；需要延迟路由时只能确认“已接收、待路由”，不能承诺旧决策已被阻止。影响决策的生效点是路由 / 控制提交与修订号更新的原子边界，L4 的“接收输入”均指此处。

路由与运行终止也必须定序：路由先提交，新输入使在求值的完成提议过期；终止先提交，路由重新判断目标。显式指向终态运行的控制输入返回目标已终止，不悄悄转交其他运行；允许启动新工作的会话输入可按规则新建运行。

只有完成路由后的运行输入才要求 `target_scope = run_id`，并进入运行级消费语义。广播在原子路由时固定目标集合，后续重试不能重新扩大集合；未来创建的运行不会自动收到历史广播。新运行的初始输入来自显式路由绑定，属于新输入交付，不是历史广播重放。

## 4. 事件、状态视图、检查点解决三个不同问题

```text
事件（Event）
→ 发生过什么？

状态视图（State View）
→ 现在是什么？

执行检查点（Execution Checkpoint）
→ 中断以后如何继续？
```

推荐关系：

```text
领域实体当前状态 + 领域事件
          │
       原子提交
          │
          ├── 状态视图
          └── 执行检查点
```

运行、动作等领域实体拥有运行时下一步决策需要的持久当前状态；领域事件保存不可变的执行历史事实。二者应作为同一次领域状态转换的持久化原子单元提交，避免“状态成功、事件失败”或反向不一致。

状态视图由当前状态与执行事实投影 / 派生，用于查询、调度、治理和展示，并且可以重建；执行检查点保存执行位置、等待条件、待处理动作、子会话、审批以及相关引用，是恢复载体而不是唯一事实源。

事件日志只是**执行历史事实源**，不等于整个真实世界的事实源，也不要求运行时采用完整事件溯源。Git、数据库、SaaS、文件系统等外部世界仍拥有自己的真实状态；运行时协调执行时可以直接读取持久领域实体当前状态，而不要求每次通过全量事件重放得到当前状态。

## 5. 不要再把所有东西都叫 State

至少需要区分：

```text
领域实体持久状态
→ 运行、动作等当前权威执行状态

状态视图
→ 面向查询、调度和治理的当前执行事实视图

执行检查点
→ 如何恢复当前运行

策略状态
→ 为保持后续决策连续性维护的策略私有状态

会话历史
→ 会话范围内的交互与历史

工作环境状态
→ 工作空间、沙箱、浏览器、Git 与外部资源状态
```

领域实体持久状态属于实现层分类，不新增为面向用户的正式领域实体。策略状态由执行框架解释，并声明运行级、会话级等作用域；运行时只负责可靠保存、恢复和引用，不把计划、待办、工作流游标等内部结构固化为运行时 Schema。

这一边界也用于理解外部 Agent 框架：不同框架里的 `State`、`Session`、`Run` 可能只是同名，必须按生命周期、所有权、持久化边界和恢复语义映射，而不能按名字直接等同。

## 6. 动作不是工具调用

动作（Action）是运行时向执行世界发出的、可治理、可追踪的**逻辑执行意图**。

```text
动作
├── 工具调用
├── MCP / API 调用
├── Shell / 代码执行
├── 浏览器操作
├── 人工请求
└── 子智能体委派
```

风险、权限、自主性、审批、可逆性和数据流策略都可以在动作级做确定性判断。

L3 定义动作生命周期；L2 决定动作实际由同步调用、Worker、远程任务、消息系统、轮询或回调执行。也就是说，动作在运行时模型中拥有独立生命周期，但底层实现不必全部异步化。

## 7. 动作与执行尝试必须分离

```text
动作
 ↓
执行尝试（Execution Attempt）
 ↓
执行尝试结果（Attempt Result）
 ↓
结果判定（Outcome Resolution）
 ↓
动作判定结果（Action Outcome）
```

一个动作可以经历多次执行尝试：

```text
动作 A1
├── 尝试 1 → 超时
├── 尝试 2 → 临时错误
└── 尝试 3 → 成功
```

逻辑业务意图仍然只有一个。这个分离使重试、幂等、恢复、成本和审计都能保持正确语义。

## 8. 超时不等于失败，结果未知必须先核对

生产系统最危险的不是明确失败，而是无法确认副作用是否已经发生：

```text
请求已发送
   ↓
外部系统可能已经完成动作
   ↓
响应丢失 / 连接超时
   ↓
结果未知
```

因此：

> **执行尝试失败不等于动作失败；超时不等于副作用没有发生。**

对于结果未知：

```text
结果未知
   ↓
结果核对
   ↓
确认外部世界实际状态
   ↓
成功 / 失败
   ↓
再决定是否创建新的执行尝试
```

同一个逻辑动作的所有执行尝试共享同一个幂等键。重试安全性由能力语义和当前动作风险共同决定，不能由模型看到错误后盲目重复执行。

补偿也不是重试。补偿应建模为新的动作，通过因果关系关联原动作，而不是修改原有执行历史。

### 8.1 持久派发与结果核对

领域状态与事件原子提交，不能覆盖外部系统的副作用。派发必须先持久化动作、执行尝试、稳定幂等身份和待派发记录，再调用 L2；已满足授权前提的首次派发记录与接受的决策及新策略状态共享提交边界；待审批动作只物化逻辑动作，审批通过后才随授权状态转换创建尝试与派发记录；后续重试的尝试和待派发记录随对应状态转换原子提交。待派发记录可直接保存在运行时存储，无需独立消息系统。

| 中断位置 | 恢复行为 |
| --- | --- |
| 意图尚未提交 | 没有可派发动作，重新求值 |
| 意图已提交，尚未获派发许可 | 重新检查准入，再从持久待派发记录继续 |
| 请求可能已到达，响应或执行引用丢失 | 按稳定身份核对；不能仅凭缺少执行引用判定未执行 |
| 结果已返回，运行时尚未提交 | 重新查询 / 接收结果并去重，再提交判定 |

派发重送复用原执行尝试身份；明确需要新的物理尝试时才创建新的尝试身份，逻辑动作的幂等键保持不变。L2 必须声明是否支持幂等去重、按稳定身份查询和取消。重送安全性取决于执行器与目标系统的实际保证，不能仅靠 L3 生成一个键。

无法核对的非幂等操作保留 `Unknown`，附带证据、下次核对时间或人工干预要求；不强制收敛成成功 / 失败，也不自动重试。具备有效去重保证的操作可以按同一身份恢复重送；仅自然幂等的操作还须确认旧尝试已停止，并满足下述共享资源准入规则。

动作协调器负责核对的调度和判定流程，L2 提供面向具体系统的查询与证据；L3 不内置 Shell、浏览器或 SaaS 的业务查询细节。运行终态后的未决核对仍需保留持久工作记录，由动作协调器继续处理，不重新启动已终止的策略。

### 8.2 派发许可与结果接收

决策被接受不等于动作可以立刻执行。每次派发，包括恢复重送和重试，都要重新检查运行 / 动作的停止标记、结构化祖先的终止要求、当前授权及审批有效性、预算 / 截止时间和资源准入；检查通过与派发许可持久化在同一控制边界完成。审批绑定动作参数和授权范围，不能将旧审批应用于改变后的请求。L2 在实际资源入口再次落实约束，不能把缓存的派发许可当作永不过期的授权。

资源占用须在允许真实执行前持久关联到执行尝试；L2 获得资源准入后才执行。若 L2 另有资源管理存储，使用尝试身份幂等预留，预留结果未知时不派发，恢复先核对；不假设两个存储之间存在隐式原子事务。进程重启不得绕过 L2 的持久阻塞规则。

第一版同一动作不启动重叠的新尝试：旧尝试仍可能执行时，仅在目标支持同一身份去重时重送；否则保持结果未知。自然幂等只说明重复操作的最终效果，不保证与其他写操作交错时安全。Shell / PTC 等复合执行的重试能力必须覆盖整个副作用范围，不能因其中某个调用幂等而重跑整个程序。

结果接收必须核验来源和动作 / 尝试关联，按来源结果身份或版本去重。重复结果不重复推进决策修订号，迟到的执行中通知不能覆盖终态；相互矛盾的结果保留证据并触发核对，不采用最后写入覆盖。结果事实、动作判定、相关运行的决策修订号和待唤醒标记一同提交；决策输入不能依赖尚未更新的异步查询视图。观察摘要可以稍后生成，其未就绪状态必须显式呈现；摘要到达改变合法输入时同样推进修订号。

子运行委派由 L3 原子建立委派动作与子运行的唯一关联；重送 / 恢复不能创建第二个子运行。其创建、取消和结果关联走 L3 生命周期协议，不假装成需要 L2 执行的外部请求。

## 9. L3 的核心领域主链

当前 L3 可以收敛为：

```text
工作单元
  ↓
会话
  ↓
运行
  ↓
动作
  ↓
执行尝试
  ↓
执行尝试结果
  ↓
结果判定
  ↓
动作判定结果
```

配套数据体系：

```text
事件
→ 发生了什么

状态视图
→ 现在是什么

执行检查点
→ 怎么继续

追踪
→ 具体怎么执行的

工作环境状态
→ 外部执行世界现在是什么
```

## 10. L3 不是一组 Manager，而是一个运行时内核

第一版运行时不需要为每个领域实体建立独立 Manager。核心责任可以压缩为三个逻辑组件：

```text
统一运行时
│
├── 运行时引擎（Runtime Engine）
│   ├── 触发器处理
│   ├── 运行生命周期
│   ├── 等待 / 唤醒
│   ├── 挂起 / 恢复
│   └── 恢复执行
│
├── 动作协调器（Action Coordinator）
│   ├── 动作创建
│   ├── 执行尝试
│   ├── 结果判定
│   ├── 重试
│   ├── 结果核对
│   └── 补偿关系
│
└── 运行时存储（Runtime Store）
    ├── 领域实体持久状态
    ├── 事件日志
    └── 执行检查点
```

运行时引擎是运行生命周期的唯一推进入口。工具网关、执行器、回调处理器或其他组件只能报告动作完成、子运行完成、审批通过等事实或信号，不能绕过运行时引擎直接修改运行生命周期。

动作协调器负责把逻辑动作解析成一次或多次真实执行尝试，并根据执行结果、外部状态和能力语义确认最终动作判定结果。它不负责具体理解 Shell、Browser、Git、MCP 等执行实现。

运行时存储的核心责任不是普通 CRUD，而是保证领域状态转换的持久一致性。第一版中，领域实体当前状态、事件日志和执行检查点可以共用 SQLite 或 PostgreSQL 等同一物理存储，不需要因为逻辑职责不同就拆成独立服务。

## 11. 执行框架与运行时之间只有稳定控制边界

执行框架负责决定“下一步想做什么”，运行时负责决定“这个决定如何成为可持久、可治理的执行事实”。

```text
执行框架
   ↓ 决策
运行时引擎
   ├── 执行动作
   ├── 定向取消
   ├── 等待
   ├── 完成
   └── 失败
```

一个执行框架步骤不是“一次模型调用”、一个工作流节点或一次 Agent Turn，而是从一个稳定决策点开始进行一次完整策略求值，直到产生需要运行时接管的决策。

运行时边界由可靠执行语义决定，而不是由是否发生 I/O 决定。执行框架必须在以下边界交还控制权：

- 产生需要独立可靠语义的受治理执行行为；
- 进入需要持久化的等待；
- 创建可独立等待、恢复、取消或完成的执行生命周期；
- 宣布本次运行完成或失败；
- 跨越权限主体或治理边界。

普通模型调用、上下文检索、记忆召回、能力发现和纯策略控制转移可以保留在执行框架内部，除非它们自身需要独立持久生命周期、恢复、调度或治理。

最小决策集合可以保持为：

```text
Execute(actions)
Cancel(targets)
Wait(condition)
Complete(output, evidence_refs)
Fail(reason)
```

一次执行决策可以产生一个或多个动作，因此运行时单写者不意味着运行内部串行。多个动作、子运行或外部任务可以并发执行；运行时只负责统一协调它们的生命周期和依赖。

执行框架不能直接修改运行、动作等运行时状态，也不能绕过动作协调器自行决定结果未知动作是否安全重试。

普通模型推理通常属于执行框架内部过程；只有当模型调用本身需要独立持久生命周期、恢复、调度或治理时，才需要把它提升为运行时动作。

### 11.1 等待登记与可靠唤醒

`Wait` 条件使用可持久化的结构化描述，第一版支持动作 / 子运行终态的任一或全部组合、截止时间，以及指定关联键的外部信号；不保存任意函数闭包。外部世界条件通过 L2 查询或信号转成可判定事实。

L3 为完成路由的运行级信号持久化唯一身份、`target_scope`、关联键和接收顺序。第一版该投递的 `target_scope` 必须指向一个运行；同一运行按持久接收顺序单消费者交付，消费记录绑定 `(signal_id, run_id)`，重复投递不能重复消费。按关联键筛选后，只确认实际处理的信号，不能通过推进单一游标跳过其他尚未消费的信号。关联键用于匹配业务条件，不决定路由或共享消费位置。动作判定、状态条件的重新求值不属于一次性信号消费。

会话级输入若需要广播，必须在原子路由时固定目标运行集合，为每个运行建立独立投递与消费记录；一个运行消费不影响其他运行。未明确目标的入口事件不得任意交给首个等待者，按 [入口路由规则](#_3-1-入口接收、路由与运行输入) 恢复已有运行、创建新运行或保留待路由状态；未来创建的运行不自动收到历史广播。等待登记保存所属运行和起始接收位置，同一运行重建等待沿用运行级消费记录，不因登记身份改变重复消费。第一版不支持同一运行内部多个独立信号订阅者；如需扩展，必须改用显式订阅者级投递与确认。

事件消费位置属于 L3；L4 只看到语义条件及信号引用，不读取事件表偏移。

等待登记必须与条件检查形成一致性边界：先保存到达的事实；登记时在同一事务 / 串行控制区间重查持久事实，再决定进入挂起还是就绪。到达与登记无论谁先发生，都必须使已满足的条件得到处理。一次性信号的消费确认与接受的决策一同提交，拒绝或崩溃不会丢弃输入。

时间等待保存绝对截止时间，恢复时立即处理已过期等待。动作状态等待是可重新求值的条件；外部信号等待必须明确从哪个语义起点接收，不能默认丢弃登记前已关联的信号。普通条件等待期间，结果未知、用户纠偏和治理中断可以提前唤醒策略；运行取消直接由控制面执行。

同一会话的策略步骤串行求值与提交，防止会话级策略状态被不同运行覆盖；该约束不限制动作并发。具体规则见 [L4 策略状态一致性](./l4-strategy-harness#会话级策略状态的并发约束)。

### 11.2 所有决策共用一个提交协议

策略状态版本、决策输入修订号与求值身份解决不同问题。L3 在短事务内登记当前有效 `evaluation_id`，并取得输入与策略状态的一致快照；它只是调用协议元数据，不是新的领域实体。求值截止时间与失败 / 无进展计数由 L3 持久管理，重启不清零；超过限制释放有效求值位置并记录干预原因。模型求值不持有数据库事务或控制面锁。同会话只允许一个有效策略求值；超时、取消或恢复替换求值时使旧身份失效，旧进程迟到返回也不能提交。

每次返回至少关联求值身份、输入修订号、策略状态版本、决策、新策略状态和明确处理的输入引用。提交按以下顺序进行：

1. 查持久回执：相同求值身份及相同返回内容已处理，直接返回原回执；相同身份却内容不同则拒绝，不重新解释。
2. 检查当前有效求值身份、输入修订号、策略状态版本、运行许可及该决策的前提。消费引用必须属于本次快照且尚未被消费；不能确认未交付或未经处理的输入。
3. 接受时原子保存回执、策略状态、明确的输入确认、决策对应的动作 / 等待 / 控制或终态记录、事件及下一步调度标记，并关闭该求值身份。提交响应丢失时查询回执，不能再次物化动作。
4. 拒绝时关闭该求值身份，只记录拒绝回执和调度处理，不提交候选策略状态、不消费输入、不物化部分动作。版本过期重新取快照，非法请求返回结构化原因。恢复优先读取回执；只重新求值未提交且已使旧身份失效的步骤。

`Execute` 的动作集合原子接受或拒绝：参数错误、确定性权限拒绝导致整批拒绝；需要异步审批的合法动作可以作为待审批动作被接受，但未获批前不能派发。`Cancel` 同样先校验整组目标，再持久化请求。拒绝反馈不保证策略状态已经前进，适用于所有决策而不只 `Complete`。

接受决策后也必须有确定的后继：`Execute` 由已持久的动作 / 审批调度继续，`Cancel` 提交后使当前运行可再次决策，`Wait` 原子检查条件后就绪或挂起，`Complete` / `Fail` 进入各自终止协议。不存在目标的等待应拒绝，不能静默永久挂起。条件已满足却重复返回相同等待、重复取消已结束目标、无变化下反复拒绝等，统一受无进展次数 / 求值预算限制；计数持久保存，达到上限保存干预原因并挂起，取消和核对控制面仍可运行。

预算耗尽或工作截止时间到达要禁止新增业务执行，但不能禁用停止、核对和资源释放。停止类控制仍需满足身份与权限前提，使用平台控制资源；不得因为业务预算用尽而等待模型先返回 `Fail` 才能停止。强制验证若消耗业务预算也必须经过相同准入，不能借门禁绕过约束。

## 12. 执行结果、动作判定结果、观察和上下文必须分层

```text
执行尝试结果
→ 这次物理执行返回了什么

动作判定结果
→ 这个逻辑动作实际上发生了什么

观察
→ 智能体应该看到什么

上下文
→ 当前模型实际加载什么
```

边界是：

```text
L4 执行框架
    ↓ 决策
L3 动作
    ↓
L2 执行尝试
    ↓
执行尝试结果
    ↓
L3 结果判定
    ↓
动作判定结果
    ↓
L2 观察投影
    ↓
观察
    ↓ 关联到运行 / 动作
L3
    ↓
L4 上下文构建器
```

因此：

> **L3 决定动作实际上发生了什么；L2 决定智能体能够观察到什么；L4 决定当前模型需要看到什么。**

L2 拥有观察内容的语义，例如如何过滤、聚合、脱敏和引用 Git、Browser、Shell、MCP 等原始结果；L3 只负责观察的生命周期、来源关联、持久引用和恢复关系，不应理解这些执行世界的具体内容。

观察也不等于上下文。执行框架可以根据当前任务只选择部分观察、摘要或引用进入当前模型工作集。

## 13. 第一目标是持久执行，而不是分布式 Worker

统一 L3 语义不意味着必须采用分布式物理部署。推荐把实现分为三个部署剖面：

```text
嵌入式运行时（Embedded Runtime）
→ 单进程协调
→ 内存 + SQLite / 本地持久化
→ 本地执行器

单节点持久化运行时（Single-node Durable Runtime）
→ 单个活动运行时进程 / Pod
→ PostgreSQL 等外部持久存储
→ 本地或远程执行器
→ 进程崩溃后恢复同一次运行

分布式运行时（Distributed Runtime）
→ 多个运行时 Worker
→ 共享持久存储
→ 运行所有权可以跨节点迁移
→ 需要租约、版本校验、隔离令牌等额外协调机制
```

第一版平台应优先建设**单节点、可持久恢复、支持并发动作和子运行的运行时**，而不是先建设分布式 Worker 集群。只有多租户规模、异构执行环境、强隔离、弹性伸缩或跨节点执行真正出现后，才引入分布式协调成本。

> **逻辑组件边界不等于物理微服务边界。**

运行时引擎、动作协调器、运行时存储、执行框架和工作环境可以在架构上保持清晰边界，但第一版完全可以位于同一个 Python / Go 进程或少量本地进程中。

同一个运行在不同部署剖面中的单写者机制可以逐级增强：

```text
嵌入式
→ Event Loop / Channel

单节点持久化
→ Event Loop + 持久状态

分布式
→ 租约 + 版本校验 + 隔离机制
```

运行时领域模型不应因为部署方式变化而改变。

## 14. 取消是请求，不是已经发生的事实

```text
CancelRequested
≠
Cancelled
```

取消表示系统希望未来执行停止；是否真正停止、外部副作用是否已经发生，仍然必须根据实际结果确认。因此取消不能回写历史，也不能把已经完成的动作改写成“已取消”。

至少需要区分三个层级：

```text
执行尝试取消
→ 尝试停止这一次物理执行

动作取消
→ 不再希望这个逻辑动作继续推进
→ 阻止新的执行尝试，并处理当前执行尝试

运行取消
→ 停止新的执行框架步骤和新动作
→ 处理活动动作、等待条件和子运行
```

取消执行尝试后，实际结果仍可能是已取消、已完成、失败或结果未知。对于已经产生的业务副作用，如果确实需要抵消，应通过新的补偿动作完成，而不是把原动作历史改写成未发生。

运行取消属于运行时控制面，即使运行当前处于挂起状态，也不需要先恢复执行框架才能处理取消。取消结构化子运行同样由 L3 发起运行取消协议，解除其普通等待并处理其活动动作与下级子运行；只有具体执行尝试的停止才进入 L2。没有活动执行的等待中子运行，也必须能通过 L3 完成取消。

强制终止与正常取消也不同：正常取消优先协作式停止并确认结果；安全、治理或资源控制触发的强制终止可以直接停止执行承载，但仍不能证明此前的外部副作用不存在。

> **终止执行，不等于撤销世界。**

### 14.1 失败终止协议

第一版接受 `Fail(reason)` 后允许运行立即进入 `Failed`，但必须在同一持久转换中关闭该运行的新策略步骤、动作、尝试与派发准入，记录失败原因，并为所有活动动作和结构化子运行登记取消请求。新策略状态及输入消费也在该转换中提交；终止决定失败则均不提交。动作 / 子运行创建与该转换按运行单写者顺序处理，不能遗漏并发新增的结构化工作。

未取得派发许可的待派发尝试停止派发；许可获取与终止提交须在同一运行控制边界定序。先获准的尝试可能已经触达世界，按在途执行请求取消与核对，不能因尚未收到响应而判为未执行。动作取消阻止重试；结构化子运行进入 L3 运行取消协议，包括等待中的子运行；独立子运行保持原生命周期。

取消请求和未决核对必须是可恢复的持久工作，运行终态不能让调度器丢弃它们。L3 继续确认实际结果和资源释放：迟到成功保持成功，结果未知保持未知，资源占用遵守 L2 阻塞规则。恢复只继续这些控制工作，不重新启动失败运行的策略，不派发原动作的新尝试。补偿是新动作，若需要执行则交给独立授权的恢复运行；失败终态本身不授予补偿权限。

例如 A、B 并行时接受 `Fail`：运行进入失败，B 被持久请求取消且禁止新尝试；B 已完成则记录其真实结果，无法确认则持续核对。进程在终止提交后崩溃，仍按同一记录继续处理 B，而不是任由执行器自行决定是否重试。

### 14.2 完成、失败与取消的仲裁

所有终止意图通过同一运行控制入口串行提交。外部运行取消先持久设置停止标记、使当前求值身份失效并登记活动动作 / 结构化子运行取消请求；此后不接受新的策略决策，也不能由迟到的 `Complete` / `Fail` 改写取消路径。反过来，完成或失败先提交，则后到取消只返回已终止事实。

三条路径的终态条件明确不同：

| 路径 | 终态条件 | 仍需处理的世界状态 |
| --- | --- | --- |
| `Complete` | 版本化证据与门禁成立；没有活动或结果未知动作；结构化子树已终止且没有未决执行 / 效果 | 后续外部变化不改变已交付版本的完成事实 |
| `Fail` | 已原子关闭执行准入并持久登记取消与核对工作，即可 `Failed` | 可以仍有在途或结果未知执行，由控制面收敛 |
| 外部运行取消 | 接受请求后先保持停止标记；直接及结构化子树中的执行均已停止或被可靠隔离、实际结果已确认，才 `Cancelled` | 无法确认则保持取消处理中并请求干预，不将请求成功误报为取消完成 |

运行取消处理中可保持 `Suspended` 并携带持久停止标记；这是控制状态，不新增必须对外统一的运行枚举。独立子运行不纳入父运行的取消 / 完成等待，但其对共享资源的影响仍受 L2 准入与证据版本约束。结构化子运行即使已经 `Failed`，也不能仅凭其终态忽略遗留的执行和未知效果。

终态写入后不回退为执行中；迟到结果更新对应动作 / 尝试和核对记录，必要时记录异常事实，但不重写父运行历史。`Complete` 要求已有运行输入均已处理，本次确认也必须遵守快照引用检查；有未处理输入则拒绝完成，不能依靠运行终止将其丢弃。失败 / 取消遗留的未处理输入保留来源与未处理标记，后续仅由显式入口路由规则处理，不冒充已消费，也不自动复活原运行。证据须由受信验证过程绑定到明确目标版本及验证条件；模型提供的任意引用不能自行成为通过门禁的依据。

## 15. 父子运行必须显式定义生命周期关系

子运行至少区分两类生命周期关系：

```text
结构化子运行（Structured Child Run）
→ 生命周期受父运行约束
→ 父运行通常等待其完成
→ 父级取消默认可向下传播

独立子运行（Detached Child Run）
→ 生命周期与父运行解耦
→ 父运行无需等待
→ 父级结束或取消不自动终止它
```

父子关系还需要表达完成、失败和取消策略，但运行时只提供可靠生命周期原语，具体业务聚合策略由执行框架或委派策略决定。

因此：

```text
ChildFailed ≠ ParentFailed
ParentCancelRequested ≠ EveryChildCancelled
```

例如研究任务中一个子运行失败，执行框架可以选择尽力聚合其他结果；父运行请求取消后，也必须分别确认各个子运行和活动动作的真实最终状态。

运行进入 `Completed / Failed / Cancelled` 等终态，也不表示外部世界已经完全收敛。仍可能存在待核对的动作、待补偿副作用或待释放执行资源：

```text
Run terminal state
≠
World fully reconciled
```

终态之后的清理、结果核对和补偿不能通过重写运行历史完成。

## 16. 恢复意味着恢复可继续执行的语义状态

恢复不是回到某一行代码，而是把同一次运行恢复成可继续决策和执行的状态：

```text
加载未完成运行
      ↓
加载领域实体持久状态
      ↓
加载执行检查点 / 策略状态
      ↓
检查待处理动作
      ↓
核对结果未知或失联执行尝试
      ↓
重建 Ready / Waiting 条件
      ↓
继续同一次运行
```

因此：

```text
Process lifetime ≠ Run lifetime
Worker failure ≠ Run failure
```

内存状态只是执行缓存。判断某个信息是否必须持久化的简单标准是：**如果此刻直接 kill -9，丢失这个信息是否会改变业务执行语义。** 如果会，它就不能只存在于进程内。

## 17. 核心不变量

1. **工作单元承载长期连续性，不能依赖智能体或会话存活。**
2. **会话是智能体与工作单元的连续关系，不等于聊天历史或上下文窗口。**
3. **运行是逻辑执行周期，不等于进程、HTTP、模型调用或工具调用。**
4. **运行可以挂起并恢复；触发器到达不等于一定创建新的运行。**
5. **进程生命周期不等于运行生命周期；进程或 Worker 失败不等于运行失败。**
6. **领域实体当前状态与领域事件应形成同一次原子持久状态转换；运行时不要求完整事件溯源。**
7. **事件、状态视图、执行检查点分别回答“发生过什么、现在是什么、怎么继续”。**
8. **状态视图、策略状态、会话历史和工作环境状态必须分离；策略状态必须具有明确作用域。**
9. **动作是逻辑执行意图，执行尝试是一次真实执行。**
10. **执行尝试失败不等于动作失败；超时不等于副作用没有发生。**
11. **结果未知必须先核对外部状态，再决定是否重试。**
12. **L4 负责策略控制，L3 负责执行生命周期控制，L2 负责真实执行、观察与验证。**
13. **执行结果、动作判定结果、观察和上下文属于不同层次，不能互相替代。**
14. **同一运行的生命周期状态转换必须保持单写者语义，但运行内部动作和子运行可以并行。**
15. **L3 的第一目标是持久执行，不是分布式；分布式协调是部署剖面的增量机制。**
16. **逻辑组件边界不等于物理微服务边界。**
17. **取消请求不等于取消完成；取消不会重写已经发生的事实。**
18. **执行尝试取消、动作取消和运行取消属于不同层级。**
19. **子运行失败不等于父运行失败；父运行取消也不等于所有子运行都已成功取消。**
20. **运行进入终态不等于外部世界已经完全核对和收敛。**
