# L3 统一运行时

> **运行时（Runtime）的核心职责不是替智能体决定怎么做，而是把真实执行变成有身份、有生命周期、可持久、可恢复、可追踪、可治理的系统事实。**

## 1. L3 管什么，不管什么

三个关键执行层的边界是：

```text
L4 执行策略 / 执行框架
→ 决定当前任务怎么推进

L3 统一运行时
→ 管理执行生命周期、事实、恢复与可靠性

L2 智能体工作环境
→ 真正执行动作并作用于外部世界
```

规划、待办、评估器、上下文策略等属于执行框架；Worker、队列、远程任务、沙箱、MCP 传输等具体执行机制属于工作环境。L3 只保留跨执行策略和执行机制都稳定的运行时语义。

## 2. 三个时间尺度：工作单元、会话、运行

```text
工作单元（Work）
   ↓
会话（Session）
   ↓
运行（Run）
```

**工作单元**承载长期工作连续性。目标、任务、共享资源、制品、工作空间、进度、治理与验收都围绕工作单元持续存在；智能体、模型和执行框架都可以被替换。

**会话**表示一个智能体与一个工作单元之间相对连续的认知 / 执行关系。它不是聊天线程，也不是上下文窗口；会话历史只是会话拥有的一类信息。

**运行**表示一次由触发器启动，并由运行时统一管理开始、挂起、恢复和终止的逻辑执行周期。它不等于 HTTP 请求、Worker、模型请求或工具调用。

## 3. 挂起不等于运行结束

运行可以暂时没有可执行动作，但仍然保持同一个逻辑生命周期：

```text
Running
   ↓
Suspended
   ↓ 条件满足
Running
   ↓
Completed / Failed / Cancelled
```

常见挂起包括等待工具、远程任务、子智能体、内部定时器或可恢复审批。

例如父智能体分叉多个子智能体并等待结果：

```text
父运行
  ↓
创建子会话 / 子运行
  ↓
父运行挂起
  ↓
子智能体完成
  ↓
父运行恢复
```

这仍然可以是同一次父运行。判断是否连续的关键不是进程是否一直存活，而是运行时是否仍然保存“正在等待什么，以及条件满足后如何继续”。

## 4. 事件、投影状态、检查点解决三个不同问题

```text
事件（Event）
→ 发生过什么？

运行时投影状态（Runtime Projection State）
→ 现在是什么？

执行检查点（Execution Checkpoint）
→ 中断以后如何继续？
```

推荐关系：

```text
动作 / 动作判定结果
       ↓
      事件
       ↓
    事件日志
       ↓
运行时投影状态

运行
 ↓
执行检查点
```

事件是追加式执行事实；运行时投影状态服务查询、调度、治理和展示，可以重建；执行检查点保存执行位置、等待条件、待处理动作、子会话、审批以及相关引用，是恢复载体而不是事实源。

事件日志只是**执行事实源**。Git、数据库、SaaS、文件系统等外部世界拥有自己的真实状态，因此 Agent Platform 不需要把整个平台做成完整事件溯源系统。

## 5. 不要再把所有东西都叫 State

至少需要区分：

```text
运行时投影状态
→ 当前执行事实视图

执行检查点
→ 如何恢复当前运行

执行框架状态
→ 规划、待办、评估器等策略私有状态

会话历史
→ 会话范围内的交互与历史

工作环境状态
→ 工作空间、沙箱、浏览器、Git 与外部资源状态
```

这一边界也用于理解外部 Agent 框架：不同框架里的 `State`、`Session`、`Run` 可能只是同名，必须按生命周期、所有权、持久化边界和恢复语义映射，而不能按名字直接等同。

## 6. 动作不是工具调用

动作（Action）是运行时向执行世界发出的、可治理、可追踪的**逻辑执行意图**。

```text
动作
├── 工具调用
├── MCP / API 调用
├── Shell / 代码执行
├── 浏览器操作
├── 人工请求
└── 子智能体委派
```

风险、权限、自主性、审批、可逆性和数据流策略都可以在动作级做确定性判断。

L3 定义动作生命周期；L2 决定动作实际由同步调用、Worker、远程任务、消息系统、轮询或回调执行。也就是说，动作在运行时模型中拥有独立生命周期，但底层实现不必全部异步化。

## 7. 动作与执行尝试必须分离

```text
动作
 ↓
执行尝试（Execution Attempt）
 ↓
执行尝试结果（Attempt Result）
 ↓
结果判定（Outcome Resolution）
 ↓
动作判定结果（Action Outcome）
```

一个动作可以经历多次执行尝试：

```text
动作 A1
├── 尝试 1 → 超时
├── 尝试 2 → 临时错误
└── 尝试 3 → 成功
```

逻辑业务意图仍然只有一个。这个分离使重试、幂等、恢复、成本和审计都能保持正确语义。

## 8. 超时不等于失败，结果未知必须先核对

生产系统最危险的不是明确失败，而是无法确认副作用是否已经发生：

```text
请求已发送
   ↓
外部系统可能已经完成动作
   ↓
响应丢失 / 连接超时
   ↓
结果未知
```

因此：

> **执行尝试失败不等于动作失败；超时不等于副作用没有发生。**

对于结果未知：

```text
结果未知
   ↓
结果核对
   ↓
确认外部世界实际状态
   ↓
成功 / 失败
   ↓
再决定是否创建新的执行尝试
```

同一个逻辑动作的所有执行尝试共享同一个幂等键。重试安全性由能力语义和当前动作风险共同决定，不能由模型看到错误后盲目重复执行。

补偿也不是重试。补偿应建模为新的动作，通过因果关系关联原动作，而不是修改原有执行历史。

## 9. L3 的核心领域主链

当前 L3 可以收敛为：

```text
工作单元
  ↓
会话
  ↓
运行
  ↓
动作
  ↓
执行尝试
  ↓
执行尝试结果
  ↓
结果判定
  ↓
动作判定结果
```

配套数据体系：

```text
事件
→ 发生了什么

运行时投影状态
→ 现在是什么

执行检查点
→ 怎么继续

追踪
→ 具体怎么执行的

工作环境状态
→ 外部执行世界现在是什么
```

## 10. 核心不变量

1. **工作单元承载长期连续性，不能依赖智能体或会话存活。**
2. **会话是智能体与工作单元的连续关系，不等于聊天历史或上下文窗口。**
3. **运行是逻辑执行周期，不等于进程、HTTP、模型调用或工具调用。**
4. **运行可以挂起并恢复；子智能体完成不会天然切断父运行。**
5. **事件、运行时投影状态、执行检查点分别回答“发生过什么、现在是什么、怎么继续”。**
6. **运行时投影状态、执行框架状态、会话历史和工作环境状态必须分离。**
7. **动作是逻辑执行意图，执行尝试是一次真实执行。**
8. **执行尝试失败不等于动作失败；超时不等于副作用没有发生。**
9. **结果未知必须先核对外部状态，再决定是否重试。**
10. **L3 定义动作生命周期和可靠性语义；L2 决定具体执行机制。**
