# L3 统一运行时

> **运行时（Runtime）的核心职责不是替智能体决定怎么做，而是把真实执行变成有身份、有生命周期、可持久、可恢复、可追踪、可治理的系统事实。**

## 1. L3 管什么，不管什么

三个关键执行层的边界是：

```text
L4 执行策略 / 执行框架
→ 决定当前任务怎么推进

L3 统一运行时
→ 管理执行生命周期、事实、恢复与可靠性

L2 智能体工作环境
→ 真正执行动作并作用于外部世界
```

规划、待办、评估器、上下文策略等属于执行框架；Worker、队列、远程任务、沙箱、MCP 传输等具体执行机制属于工作环境。L3 只保留跨执行策略和执行机制都稳定的运行时语义。

## 2. 三个时间尺度：工作单元、会话、运行

```text
工作单元（Work）
   ↓
会话（Session）
   ↓
运行（Run）
```

**工作单元**承载长期工作连续性。目标、任务、共享资源、制品、工作空间、进度、治理与验收都围绕工作单元持续存在；智能体、模型和执行框架都可以被替换。

**会话**表示一个智能体与一个工作单元之间相对连续的认知 / 执行关系。它不是聊天线程，也不是上下文窗口；会话历史只是会话拥有的一类信息。

**运行**表示一次由触发器启动，并由运行时统一管理开始、挂起、恢复和终止的逻辑执行周期。它不等于 HTTP 请求、Worker、模型请求或工具调用。

## 3. 挂起不等于运行结束

运行可以暂时没有可执行动作，但仍然保持同一个逻辑生命周期：

```text
Ready
  ↓
Running
  ↓
Suspended
  ↓ 条件满足
Ready
  ↓
Running
  ↓
Completed / Failed / Cancelled
```

常见挂起包括等待工具、远程任务、子智能体、内部定时器或可恢复审批。

例如父智能体分叉多个子智能体并等待结果：

```text
父运行
  ↓
创建子会话 / 子运行
  ↓
父运行挂起
  ↓
子智能体完成
  ↓
父运行恢复
```

这仍然可以是同一次父运行。判断是否连续的关键不是进程是否一直存活，而是运行时是否仍然保存“正在等待什么，以及条件满足后如何继续”。

触发器只表示“有理由重新评估某个执行生命周期”，不等于一定创建新运行。用户输入、动作完成、子运行完成、人工审批、定时器或外部信号到达后，运行时需要判断是恢复现有挂起运行，还是创建新的运行。

## 4. 事件、状态视图、检查点解决三个不同问题

```text
事件（Event）
→ 发生过什么？

状态视图（State View）
→ 现在是什么？

执行检查点（Execution Checkpoint）
→ 中断以后如何继续？
```

推荐关系：

```text
领域实体当前状态 + 领域事件
          │
       原子提交
          │
          ├── 状态视图
          └── 执行检查点
```

运行、动作等领域实体拥有运行时下一步决策需要的持久当前状态；领域事件保存不可变的执行历史事实。二者应作为同一次领域状态转换的持久化原子单元提交，避免“状态成功、事件失败”或反向不一致。

状态视图由当前状态与执行事实投影 / 派生，用于查询、调度、治理和展示，并且可以重建；执行检查点保存执行位置、等待条件、待处理动作、子会话、审批以及相关引用，是恢复载体而不是唯一事实源。

事件日志只是**执行历史事实源**，不等于整个真实世界的事实源，也不要求运行时采用完整事件溯源。Git、数据库、SaaS、文件系统等外部世界仍拥有自己的真实状态；运行时协调执行时可以直接读取持久领域实体当前状态，而不要求每次通过全量事件重放得到当前状态。

## 5. 不要再把所有东西都叫 State

至少需要区分：

```text
领域实体持久状态
→ 运行、动作等当前权威执行状态

状态视图
→ 面向查询、调度和治理的当前执行事实视图

执行检查点
→ 如何恢复当前运行

执行框架状态
→ 规划、待办、评估器等策略私有状态

会话历史
→ 会话范围内的交互与历史

工作环境状态
→ 工作空间、沙箱、浏览器、Git 与外部资源状态
```

领域实体持久状态属于实现层分类，不新增为面向用户的正式领域实体。执行框架状态由执行框架解释；运行时只负责版本化保存、恢复和引用，不把计划、待办、评估器等内部结构固化为运行时 Schema。

这一边界也用于理解外部 Agent 框架：不同框架里的 `State`、`Session`、`Run` 可能只是同名，必须按生命周期、所有权、持久化边界和恢复语义映射，而不能按名字直接等同。

## 6. 动作不是工具调用

动作（Action）是运行时向执行世界发出的、可治理、可追踪的**逻辑执行意图**。

```text
动作
├── 工具调用
├── MCP / API 调用
├── Shell / 代码执行
├── 浏览器操作
├── 人工请求
└── 子智能体委派
```

风险、权限、自主性、审批、可逆性和数据流策略都可以在动作级做确定性判断。

L3 定义动作生命周期；L2 决定动作实际由同步调用、Worker、远程任务、消息系统、轮询或回调执行。也就是说，动作在运行时模型中拥有独立生命周期，但底层实现不必全部异步化。

## 7. 动作与执行尝试必须分离

```text
动作
 ↓
执行尝试（Execution Attempt）
 ↓
执行尝试结果（Attempt Result）
 ↓
结果判定（Outcome Resolution）
 ↓
动作判定结果（Action Outcome）
```

一个动作可以经历多次执行尝试：

```text
动作 A1
├── 尝试 1 → 超时
├── 尝试 2 → 临时错误
└── 尝试 3 → 成功
```

逻辑业务意图仍然只有一个。这个分离使重试、幂等、恢复、成本和审计都能保持正确语义。

## 8. 超时不等于失败，结果未知必须先核对

生产系统最危险的不是明确失败，而是无法确认副作用是否已经发生：

```text
请求已发送
   ↓
外部系统可能已经完成动作
   ↓
响应丢失 / 连接超时
   ↓
结果未知
```

因此：

> **执行尝试失败不等于动作失败；超时不等于副作用没有发生。**

对于结果未知：

```text
结果未知
   ↓
结果核对
   ↓
确认外部世界实际状态
   ↓
成功 / 失败
   ↓
再决定是否创建新的执行尝试
```

同一个逻辑动作的所有执行尝试共享同一个幂等键。重试安全性由能力语义和当前动作风险共同决定，不能由模型看到错误后盲目重复执行。

补偿也不是重试。补偿应建模为新的动作，通过因果关系关联原动作，而不是修改原有执行历史。

## 9. L3 的核心领域主链

当前 L3 可以收敛为：

```text
工作单元
  ↓
会话
  ↓
运行
  ↓
动作
  ↓
执行尝试
  ↓
执行尝试结果
  ↓
结果判定
  ↓
动作判定结果
```

配套数据体系：

```text
事件
→ 发生了什么

状态视图
→ 现在是什么

执行检查点
→ 怎么继续

追踪
→ 具体怎么执行的

工作环境状态
→ 外部执行世界现在是什么
```

## 10. L3 不是一组 Manager，而是一个 Runtime Kernel

第一版运行时不需要为每个领域实体建立独立 Manager。核心责任可以压缩为三个逻辑组件：

```text
统一运行时
│
├── 运行时引擎（Runtime Engine）
│   ├── 触发器处理
│   ├── 运行生命周期
│   ├── 等待 / 唤醒
│   ├── 挂起 / 恢复
│   └── 恢复执行
│
├── 动作协调器（Action Coordinator）
│   ├── 动作创建
│   ├── 执行尝试
│   ├── 结果判定
│   ├── 重试
│   ├── 结果核对
│   └── 补偿关系
│
└── 运行时存储（Runtime Store）
    ├── 领域实体持久状态
    ├── 事件日志
    └── 执行检查点
```

运行时引擎是运行生命周期的唯一推进入口。工具网关、执行器、回调处理器或其他组件只能报告动作完成、子运行完成、审批通过等事实或信号，不能绕过运行时引擎直接修改运行生命周期。

动作协调器负责把逻辑动作解析成一次或多次真实执行尝试，并根据执行结果、外部状态和能力语义确认最终动作判定结果。它不负责具体理解 Shell、Browser、Git、MCP 等执行实现。

运行时存储的核心责任不是普通 CRUD，而是保证领域状态转换的持久一致性。第一版中，领域实体当前状态、事件日志和执行检查点可以共用 SQLite 或 PostgreSQL 等同一物理存储，不需要因为逻辑职责不同就拆成独立服务。

## 11. 执行框架与运行时之间只有稳定控制边界

执行框架负责决定“下一步想做什么”，运行时负责决定“这个决定如何成为可持久、可治理的执行事实”。

```text
执行框架
   ↓ 决策
运行时引擎
   ├── 执行动作
   ├── 等待
   ├── 完成
   └── 失败
```

一个执行框架步骤不是“一次模型调用”，而是执行框架从当前输入出发推进决策，直到遇到必须把控制权交回运行时的边界。

执行框架必须在以下边界交还控制权：

- 产生需要治理的外部副作用；
- 进入可能跨进程生命周期的长期等待；
- 宣布本次运行完成或失败；
- 发生需要运行时控制面处理的控制权转移。

最小决策集合可以保持为：

```text
Execute(actions)
Wait(condition)
Complete(output)
Fail(reason)
```

一次执行决策可以产生一个或多个动作，因此运行时单写者不意味着运行内部串行。多个动作、子运行或外部任务可以并发执行；运行时只负责统一协调它们的生命周期和依赖。

执行框架不能直接修改运行、动作等运行时状态，也不能绕过动作协调器自行决定结果未知动作是否安全重试。

普通模型推理通常属于执行框架内部过程；只有当模型调用本身需要独立持久生命周期、恢复、调度或治理时，才需要把它提升为运行时动作。

## 12. 执行结果、动作判定结果、观察和上下文必须分层

```text
执行尝试结果
→ 这次物理执行返回了什么

动作判定结果
→ 这个逻辑动作实际上发生了什么

观察
→ 智能体应该看到什么

上下文
→ 当前模型实际加载什么
```

边界是：

```text
L4 执行框架
    ↓ 决策
L3 动作
    ↓
L2 执行尝试
    ↓
执行尝试结果
    ↓
L3 结果判定
    ↓
动作判定结果
    ↓
L2 观察投影
    ↓
观察
    ↓ 关联到运行 / 动作
L3
    ↓
L4 上下文构建器
```

因此：

> **L3 决定动作实际上发生了什么；L2 决定智能体能够观察到什么；L4 决定当前模型需要看到什么。**

L2 拥有观察内容的语义，例如如何过滤、聚合、脱敏和引用 Git、Browser、Shell、MCP 等原始结果；L3 只负责观察的生命周期、来源关联、持久引用和恢复关系，不应理解这些执行世界的具体内容。

观察也不等于上下文。执行框架可以根据当前任务只选择部分观察、摘要或引用进入当前模型工作集。

## 13. 第一目标是持久执行，而不是分布式 Worker

统一 L3 语义不意味着必须采用分布式物理部署。推荐把实现分为三个部署剖面：

```text
嵌入式运行时（Embedded Runtime）
→ 单进程协调
→ 内存 + SQLite / 本地持久化
→ 本地执行器

单节点持久化运行时（Single-node Durable Runtime）
→ 单个活动运行时进程 / Pod
→ PostgreSQL 等外部持久存储
→ 本地或远程执行器
→ 进程崩溃后恢复同一次运行

分布式运行时（Distributed Runtime）
→ 多个运行时 Worker
→ 共享持久存储
→ 运行所有权可以跨节点迁移
→ 需要租约、版本校验、隔离令牌等额外协调机制
```

第一版平台应优先建设**单节点、可持久恢复、支持并发动作和子运行的运行时**，而不是先建设分布式 Worker 集群。只有多租户规模、异构执行环境、强隔离、弹性伸缩或跨节点执行真正出现后，才引入分布式协调成本。

> **逻辑组件边界不等于物理微服务边界。**

运行时引擎、动作协调器、运行时存储、执行框架和工作环境可以在架构上保持清晰边界，但第一版完全可以位于同一个 Python / Go 进程或少量本地进程中。

同一个运行在不同部署剖面中的单写者机制可以逐级增强：

```text
嵌入式
→ Event Loop / Channel

单节点持久化
→ Event Loop + 持久状态

分布式
→ 租约 + 版本校验 + 隔离机制
```

运行时领域模型不应因为部署方式变化而改变。

## 14. 取消是请求，不是已经发生的事实

```text
CancelRequested
≠
Cancelled
```

取消表示系统希望未来执行停止；是否真正停止、外部副作用是否已经发生，仍然必须根据实际结果确认。因此取消不能回写历史，也不能把已经完成的动作改写成“已取消”。

至少需要区分三个层级：

```text
执行尝试取消
→ 尝试停止这一次物理执行

动作取消
→ 不再希望这个逻辑动作继续推进
→ 阻止新的执行尝试，并处理当前执行尝试

运行取消
→ 停止新的执行框架步骤和新动作
→ 处理活动动作、等待条件和子运行
```

取消执行尝试后，实际结果仍可能是已取消、已完成、失败或结果未知。对于已经产生的业务副作用，如果确实需要抵消，应通过新的补偿动作完成，而不是把原动作历史改写成未发生。

运行取消属于运行时控制面，即使运行当前处于挂起状态，也不需要先恢复执行框架才能处理取消。

强制终止与正常取消也不同：正常取消优先协作式停止并确认结果；安全、治理或资源控制触发的强制终止可以直接停止执行承载，但仍不能证明此前的外部副作用不存在。

> **终止执行，不等于撤销世界。**

## 15. 父子运行必须显式定义生命周期关系

子运行至少区分两类生命周期关系：

```text
结构化子运行（Structured Child Run）
→ 生命周期受父运行约束
→ 父运行通常等待其完成
→ 父级取消默认可向下传播

独立子运行（Detached Child Run）
→ 生命周期与父运行解耦
→ 父运行无需等待
→ 父级结束或取消不自动终止它
```

父子关系还需要表达完成、失败和取消策略，但运行时只提供可靠生命周期原语，具体业务聚合策略由执行框架或委派策略决定。

因此：

```text
ChildFailed ≠ ParentFailed
ParentCancelRequested ≠ EveryChildCancelled
```

例如研究任务中一个子运行失败，执行框架可以选择尽力聚合其他结果；父运行请求取消后，也必须分别确认各个子运行和活动动作的真实最终状态。

运行进入 `Completed / Failed / Cancelled` 等终态，也不表示外部世界已经完全收敛。仍可能存在待核对的动作、待补偿副作用或待释放执行资源：

```text
Run terminal state
≠
World fully reconciled
```

终态之后的清理、结果核对和补偿不能通过重写运行历史完成。

## 16. 恢复意味着恢复可继续执行的语义状态

恢复不是回到某一行代码，而是把同一次运行恢复成可继续决策和执行的状态：

```text
加载未完成运行
      ↓
加载领域实体持久状态
      ↓
加载执行检查点 / 执行框架状态
      ↓
检查待处理动作
      ↓
核对结果未知或失联执行尝试
      ↓
重建 Ready / Waiting 条件
      ↓
继续同一次运行
```

因此：

```text
Process lifetime ≠ Run lifetime
Worker failure ≠ Run failure
```

内存状态只是执行缓存。判断某个信息是否必须持久化的简单标准是：**如果此刻直接 kill -9，丢失这个信息是否会改变业务执行语义。** 如果会，它就不能只存在于进程内。

## 17. 核心不变量

1. **工作单元承载长期连续性，不能依赖智能体或会话存活。**
2. **会话是智能体与工作单元的连续关系，不等于聊天历史或上下文窗口。**
3. **运行是逻辑执行周期，不等于进程、HTTP、模型调用或工具调用。**
4. **运行可以挂起并恢复；触发器到达不等于一定创建新的运行。**
5. **进程生命周期不等于运行生命周期；进程或 Worker 失败不等于运行失败。**
6. **领域实体当前状态与领域事件应形成同一次原子持久状态转换；运行时不要求完整事件溯源。**
7. **事件、状态视图、执行检查点分别回答“发生过什么、现在是什么、怎么继续”。**
8. **状态视图、执行框架状态、会话历史和工作环境状态必须分离。**
9. **动作是逻辑执行意图，执行尝试是一次真实执行。**
10. **执行尝试失败不等于动作失败；超时不等于副作用没有发生。**
11. **结果未知必须先核对外部状态，再决定是否重试。**
12. **执行框架负责决策，运行时负责生命周期和持久语义，工作环境负责真实执行与观察。**
13. **执行结果、动作判定结果、观察和上下文属于不同层次，不能互相替代。**
14. **同一运行的生命周期状态转换必须保持单写者语义，但运行内部动作和子运行可以并行。**
15. **L3 的第一目标是持久执行，不是分布式；分布式协调是部署剖面的增量机制。**
16. **逻辑组件边界不等于物理微服务边界。**
17. **取消请求不等于取消完成；取消不会重写已经发生的事实。**
18. **执行尝试取消、动作取消和运行取消属于不同层级。**
19. **子运行失败不等于父运行失败；父运行取消也不等于所有子运行都已成功取消。**
20. **运行进入终态不等于外部世界已经完全核对和收敛。**
